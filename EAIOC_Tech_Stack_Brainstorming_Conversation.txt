"What are the execution patterns of EAIOC?"

1. Which capabilities run on every request?
2. Which capabilities run asynchronously?
3. Which capabilities require long-running state?
4. Which capabilities are CPU-intensive?
5. Which capabilities require sub-10ms decisions?
6. Which capabilities can run eventually/async?
7. Which capabilities must scale independently?

If we map every approved EAIOC capability into these categories, the technology stack decision becomes much more objective and defensible.

Primary runtime: Java

Java 25

Spring Boot 4.1.x

EAIOC's core is primarily a decision/orchestration/state-management system, not a numerical-computing engine.

That makes Java a very good center of gravity.

So, in one sentence:

My first choice is a standalone EAIOC gateway/control service with a Java 25 + Spring Boot request-critical core, PostgreSQL + Redis as the initial state substrate, Python 3.14 for evaluation/intelligence workloads, Go reserved for benchmark-proven hot paths, and an evolution path to Kafka + Kubernetes + enterprise adapters.

And the first proof environment is:

A controlled generic AI application with a tool-using agent, because it exercises the broadest meaningful EAIOC capability set while keeping the experiment completely under our control.

That is the stack I would personally take forward before we start implementation.

The next logical step is not coding yet. It is to take this proposed stack and run one final Capability → Workload → Runtime → Technology validation matrix against the complete EAIOC capability set. That will tell us whether any part of this selection needs to change before we freeze it.
