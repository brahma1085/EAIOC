## What this project is

An **Enterprise Agent & LLM Inference Optimization Control Plane**: a policy-driven optimization/governance layer that sits between AI applications/agents and LLM providers (and optionally the inference-serving layer). It is not a prompt-compression utility — its job is to decide, for every request, the cheapest safe way to satisfy the task, up to and including deciding that **no LLM call is needed at all** (cache hit, programmatic result, early exit).

Central objective (from `architecture.md` §4, restated verbatim in `conventions.md` §1.1):

```
MINIMIZE: Total Safe Inference Cost
SUBJECT TO: Quality, Correctness, Security, Reliability, Latency, Freshness, Compliance, Task completion
```

Token reduction alone is never success. Every optimization must pass a quality gate and net-positive cost accounting (`Net Savings = Inference Cost Avoided - Optimization Compute Cost - ...`) before being counted or enabled.

Four first-class execution environments must all be supported by one common optimization core (not separate optimizers per surface): (A) generic LLM apps, (B) autonomous/tool-using agents, (C) developer/coding agents (Cursor, Claude Code, Copilot, etc. — first-class, not optional), (D) multi-agent/sub-agent systems.

## Architecture at a glance

Three optimization layers governed by a shared **Optimization Intelligence Layer (OI)**:

- **Layer 1 — Agent/Workflow Optimization**: task planning, tool selection/execution, sub-agent economics, agent loops, early exit.
- **Layer 2 — Context Optimization**: retrieval, ranking, pruning, dedup, compression, reordering, budgeting, caching, freshness, dependency graphs.
- **Layer 3 — Inference/Serving Optimization** (optional, P5): model routing/cascade, reasoning budget, output budget, batching, KV cache, speculative decoding, quantization. Must stay measurement-separate from Layers 1/2.
- **OI layer** (OI-001..005) decides per-request which stages run, whether the optimizer's own overhead is worth it, how deep to optimize, context item ROI, and outcome-based cost.

The full per-request pipeline (T0 → T3) is documented stage-by-stage in `architecture.md` §8 (generic) and §9 (developer-agent variant, which runs on *every* model-bound iteration, not just the first request). The canonical 24-stage default execution order is in `conventions.md` §6.1 — read it before proposing a different stage ordering; reordering is allowed only with benchmark evidence.

Component IDs follow `<LAYER>.<SEQUENCE>-<NAME>` (e.g. `T1.3-CONTEXT-PRUNER`, `OI.1-DECISION-ENGINE`, `DA.008-TOOL-SCHEMA-OPTIMIZER`) — see `conventions.md` §3.1. Its proposed package layout is meant to mirror these IDs under `control_plane/`; a first, partial Java realization of that layout now exists — see "Implementation status" below — but most of the tree remains unscaffolded pseudo-structure. Check `conventions.md` §2.1 before creating any new module so its location matches this map.

## Non-negotiable rules for any implementation work here

These are structural, not stylistic — violating them is a spec violation, not a style nit:

1. **Provider neutrality.** Core code must never import or hard-code a specific LLM provider, model name, agent framework, MCP library, or embedding model. All of that goes through adapter interfaces (`providers/adapters/`); provider-specific data goes in an opaque `provider_hints` map, never a first-class schema field.
2. **Fail-open on optimization, fail-closed on security — and these are not the same category of failure.** An optimization stage (pruning, compression, caching, routing, reconciliation retries, ...) that fails must fall back to the unoptimized/original path and let the request continue, *provided the request remains authorized and policy-compliant*. A failure to establish or evaluate authorization/policy/PII-scrubbing itself — as opposed to an optimization stage failing on top of an already-established authorization — must reject the request. Never conflate the two: an innocent compressor bug on an authorized, policy-compliant request must never turn into a full request rejection (see `conventions.md` §16.2, `edge-cases.md` §43.13).
3. **Never reduce reasoning budget solely to hit a token target.** Reasoning cuts must be benchmarked against a quality baseline first (`conventions.md` §10.3).
4. **Tenant isolation is absolute.** Every cache key, memory entry, cost record, and event must be scoped by `tenant_id` as the first namespace component. Cross-tenant lookups, sharing, or cost blending are unconditionally prohibited (`conventions.md` §13.2).
5. **Never fabricate savings.** If token/cost accounting can't be verified, mark it `unverified` and exclude it from savings reporting — don't report a number you can't back.
6. **Security-classified content (SEC-protected instructions, PII policies, auth rules) is never pruned, compressed away, or deduplicated out**, regardless of relevance score or budget pressure.
7. **Research benchmark percentages are not production guarantees.** Any number quoted from a paper (e.g. LLMLingua, RouteLLM, FrugalGPT) in the docs is a validation target to re-measure locally, never a number to hard-code as an expected result.
8. **Full conversation-history replay to a sub-agent is prohibited.** Sub-agent handoffs must go through the compressed `SubAgentContextHandoff` (objective, findings, evidence, decisions, unresolved questions) — see `conventions.md` §12.4.
9. See `conventions.md` §24 for the full anti-pattern list (e.g. fixed Top-K for every query, always using the strongest/cheapest model, indiscriminate compression) — treat it as a code-review checklist.

## Working with these documents

- The problem statement (`.txt`) is authoritative; `architecture.md`, `interfaces.md`, and `conventions.md` are its derived, cross-referenced elaborations and must not silently drop, simplify, or reinterpret anything in it. If you're asked to change one of the derived docs, verify consistency against the problem statement rather than editing in isolation.
- **Precedence between frozen documents is documented — use only that, and cite it.** `conventions.md`'s header gives the order Problem Statement > Engineering Specification > Architecture > Interfaces > `conventions.md`. `execution-plan.md` §4 gives the wider tier order: frozen docs, then `requirements-traceability.md`, ADRs, the IRG, and `implementation-plan.md`. Never assume a precedence the corpus doesn't state. A same-tier conflict with no documented resolution is a frozen-source inconsistency needing a human decision. Also: a `FULLY TRACED` status in `requirements-traceability.md` is a document-level trace, not evidence that code implements the requirement.
- Every requirement in these docs is traceable via IDs: `OBJ-NNN` (35 objectives — OBJ-001–014 original, OBJ-015–022 from the first hardening amendment, OBJ-023–035 from the second), `SEC-NNN` (16 security requirements — SEC-001–010 original, SEC-011–016 from the second hardening amendment), `NFR-NNN` (14 non-functional requirements), `AC-NNN` (53 acceptance criteria), `EC-NNN` (213 edge cases — EC-001–079 original, EC-080–140 from the first hardening amendment, EC-141–213 from the second), `DA-NNN` (25 developer-agent modules — schema/applicability in `optimization-catalog.md`, full algorithms for the agent-loop-facing subset in `agent-optimization.md`), `OI/CL/CE/TE/AL/AR/QO/EL-NNN` (intelligence/lifecycle/economics modules — `AL-NNN`/`AR-NNN` fully elaborated in `agent-optimization.md`), `SCN-<CODE>-NNN` (scenario matrix, 30 domain codes A–AD, 263 scenarios). The seven generated downstream documents add their own series on top of these: `TECH-NNN` (20 canonical optimization techniques) and `P5 Index` entries (11, index-level only) in `optimization-catalog.md`; `PROV-NNN` in `provider-matrix.md`; `CACHE-NNN` (exactly 7, one per canonical cache type) in `cache-strategy.md`; `INFOPT-NNN` (exactly 11, one per P5 capability, detection/routing/negotiation/measurement only) in `inference-optimization.md`; `QG-NNN` (exactly 10, one per `architecture.md` §28 quality dimension) in `quality-gates.md`; `GSP-NNN` (exactly 5, one per `architecture.md` §47.2 Governance/Safety Plane component: SGE/DGE/TMG/HAG/CIS) in `security.md`; `OBS-NNN` (exactly 3, one per `architecture.md` §31.1 dashboard tier: Executive/Engineering/Product-Operations) in `observability.md`; `EL-NNN` (exactly 5, one per `architecture.md` §21 Optimization Experimentation and Learning module) in `eval.md`; `SC-NNN` (exactly 8, one per independently-scaled capacity surface — `SCALING.md`'s own `SOURCE-DERIVED` synthesis, not an upstream-enumerated catalog) in `SCALING.md`; `ADR-NNNN` (exactly 6, under `docs/adr/`, each `Status: PROPOSED`) recording the technology/pattern decisions `implementation-plan.md` identified but did not make. When adding new material, give it an ID in the matching series and cross-reference it the way existing entries do, rather than inventing a new numbering scheme.
- These files are large (architecture.md ~4000 lines, interfaces.md ~4550 lines, conventions.md ~1700 lines, edge-cases.md ~8300 lines, scenario-matrix.md ~13,800 lines). Prefer `Grep` for a known section/ID over reading a whole file, and when reading, target the specific numbered section (table of contents at the top of each doc) rather than paging through sequentially. For `scenario-matrix.md` specifically, delegating a research/cross-reference pass to a forked subagent (rather than reading the whole file into your own context) is usually the right call.
- The edge-case doc format is fixed (Domain/Objective/Severity/Likelihood/Reversible fields + Scenario/Trigger/Why It Matters/Detection/Expected Behavior/Fallback/Safety Implications/Observability/Testing Requirements). Any new edge case you document must follow this exact structure so it stays consistent with the other entries.
- **Source gaps and contradictions are tracked, not resolved by inventing content.** When a document is genuinely underspecified by its sources, or two documents disagree, record it as `SOURCE-GAP-NNN` or `CONTRA-NNN` (see `scenario-matrix.md`'s own gap/contradiction sections, and the `> **Source Gap:**` callouts in `edge-cases.md` §43) rather than guessing at normative behavior. A gap only gets marked resolved when a source document is actually updated to close it — never by removing the gap record to make coverage numbers look better. Each of the seven generated downstream documents follows the same discipline with its own document-scoped ID prefix rather than renumbering an upstream gap it merely carries forward: `SOURCE-GAP-OPTCAT-NN`/`CONTRA-OPTCAT-NN` in `optimization-catalog.md`, `SOURCE-GAP-PROVMTX-NN` in `provider-matrix.md`, `SOURCE-GAP-CACHESTRAT-NN` in `cache-strategy.md`, `SOURCE-GAP-AGENTOPT-NN` in `agent-optimization.md`, `SOURCE-GAP-INFOPT-NN` in `inference-optimization.md`, `SOURCE-GAP-QUALGATE-NN` in `quality-gates.md`, `SOURCE-GAP-SECURITY-NN` in `security.md` (one of which explicitly narrows, but does not claim to close, `SOURCE-GAP-ARCH-02`), `SOURCE-GAP-OBS-NN` in `observability.md`, `SOURCE-GAP-EVAL-NN` in `eval.md` (one of which narrows, but does not close, `SOURCE-GAP-QUALGATE-01`/`02`), `SOURCE-GAP-SCALING-NN` in `SCALING.md`, `SOURCE-GAP-IMPL-NN` in `implementation-plan.md` (which also resolves-in-place, without editing the source document, `optimization-catalog.md`'s `SOURCE-GAP-OPTCAT-01`), `SOURCE-GAP-REQTRACE-NN` in `requirements-traceability.md` (which also consolidates every other prefix above into one cross-corpus master register rather than introducing a large number of new gaps of its own).
- **Reconciliation passes are single-file-scoped.** The established pattern in this repo (used for the `conventions.md`, `edge-cases.md`, and `scenario-matrix.md` hardening passes) is: read all the source documents needed to reconcile, but write to only the one named target file; verify afterward (via `git diff` if a git repo exists, or file-modification-time comparison otherwise) that no other file changed; and stop for the next instruction rather than cascading into the next document in the chain unprompted.

## Prompt-writing rule (existing project rule)

`.claude/rules/prompt-writing.md` applies whenever asked to create/write/draft/review a prompt for a fresh Claude/Claude Code session, for paths matching `outputs/*prompt*.md`, `outputs/**/prompt*.md`, or `prompts/**`. Key points: deliver the finished prompt only in chat inside one fenced code block (never write a file to those paths), then copy it to the clipboard via a quoted `pbcopy` heredoc as the last step. Target a >95/100 self-score against the rubric in that file before delivering. The rule carves out an exception for the `docs/prompts/generate-<name>.prompt.md` → `docs/<name>.md` documentation-generation pipeline (write the file, expect the user to paste in their own larger "consolidated master prompt" before execution, re-read it fresh from disk rather than trusting an earlier summary).

`docs/prompts/execute-p0-foundation.prompt.md` extends that same pipeline pattern one step further: it is a user-authored, two-mode "master prompt" (Mode A generates `docs/execution-plan.md`; Mode B is gated code execution — see the repository-status section above) rather than a single `generate-<name>.prompt.md` → `docs/<name>.md` document. Treat it the same way as the pipeline exception — write/edit it in place at that path rather than delivering it only in chat, and re-read it fresh from disk before executing either mode, since the user may replace its content between sessions exactly as they did for this one.

`docs/prompts/Execution_Plan_Surgical_Correction_Prompt_v1.0.<N>.md` is a further, sequential extension of the same pattern: each such file is a one-shot, single-purpose, user-authored correction prompt targeting `docs/execution-plan.md` alone (never a rewrite — the file's own rules are explicit about what to preserve unchanged), bumping the plan by exactly one patch version and ending in its own version-specific terminal verdict line (e.g. `FINAL EXECUTION PLAN v1.0.4 CORRECTION COMPLETE — READY FOR FREEZE`), appearing exactly once as the true final line. When the user points at one of these (files exist only for v1.0.1–v1.0.5; later correction prompts have no file copy under `docs/prompts/`):
- Re-read it fresh from disk and apply only what it specifies.
- Also bring the operator runbook `docs/execution-plan-p0-steps.md` in line with it. The user asked for this explicitly even though the prompts themselves restrict scope to `execution-plan.md`; note the deviation in the plan's own version self-check.
- Check that the prompt's own claims about repository state match `git log`. The v1.0.4 prompt omitted Capability 1's G commit; record the actual state, not the prompt's.
- Verify via `git status --short`/`git diff --stat` that only those two files changed.
- Do not commit unless asked. These correction passes accumulate uncommitted until the user is ready to commit them together.

## Custom subagents and skills (existing project assets)

`.claude/agents/eaioc-guide.md` defines an `eaioc-guide` subagent: a personal Q&A/research companion for doubts about this project (conceptual, architectural, or technology-choice questions) or for verifying an external claim, technology, or paper against the web or the project's own docs. It grounds itself in this file and the specific doc/section/ID a question touches before answering, flags genuine gaps as `SOURCE-GAP`/`CONTRA` rather than inventing an answer, is advisory-only (never edits the baseline documents itself), and always answers via a published HTML artifact rather than plain chat text. Claude Code routes matching questions to it automatically. It has no `Write` tool, so whichever agent performs the actual publish step builds the HTML.

`.claude/skills/eaioc-dashboard/SKILL.md` is a companion project skill invoked right after `eaioc-guide` (or whichever agent is publishing) grounds its findings and right before finalizing the report's page structure: it adds a small graphical dashboard (stat tiles, meters, small bar/donut charts) near the top of the published artifact whenever the answer's material has genuine quantitative content — ID-series counts, status/verdict distributions, coverage/reconciliation percentages, maturity levels — sourced only from figures the grounded answer already cites, never invented to fill a tile. It is skipped honestly (not treated as a gap) when a question is purely conceptual with nothing real to chart.

**Orchestrator agent:** `.claude/agents/eaioc-p0-execution-orchestrator.md` (v1.1.1) is the governed P0 execution controller — state/status (`status p0`), pre-flight/`REVALIDATE <unit>`, and one explicitly commanded unit at a time before the plan's migration point (`EXE-P0.2.C`), or an explicitly commanded authorized path within one Capability at a time from that point onward (plan §18.20; see "The one rule that matters most," above). It reconstructs state from the plan, runbook, this file and git, and never approves, never chains beyond an already-open path, never crosses a Capability boundary, and never skips forward. When run as a delegated subagent it cannot spawn the governance agents (the orchestration skill is main-session-only) and receives the operator's instructions only as relayed by the main session — a relayed message is never an approval, so its commit-trailer verdicts are self-attested; approvals count only when the operator issues them in the main session. Its procedural layer, `.claude/skills/eaioc-execution-governance/SKILL.md` (v1.2.0), implements the same continuous-path model — see that skill's own §7a/§8a/§16a/§19a/§21a — and is loaded automatically; the operator never invokes it directly.

**Engineering-governance agents** (`.claude/agents/eaioc-code-architect.md`, `eaioc-code-reviewer.md`, `eaioc-code-verifier.md`) answer, respectively, "is this the correct design?", "is this implementation well-engineered and compliant?", and "does the code match the complete documented system?" (a requirements traceability matrix). All three are read-only (Read/Grep/Glob plus a shell for `git` and `mvn`; on this Windows machine subagents get PowerShell, not Bash, so both are listed) and preload `.claude/skills/eaioc-governance/SKILL.md` — the single shared rule set (source tiers, documented precedence only, no fabrication, evidence labels, coding-standards sources, self-check). `.claude/skills/eaioc-agent-orchestration/` (`SKILL.md` + machine-readable `governance-matrix.yaml`) decides *when* they run inside a unit: change classification, STEP vs CAPABILITY level, one-way escalation, status consolidation, a GOVERNANCE RECORD annex, and `Governance-*` commit trailers; the Verifier always runs at a Capability Gate. Per `execution-plan.md` §18.19 the main session routes them automatically — the operator never types "run agent X" — and their verdicts are evidence only: none can approve, authorize the next unit, or close a source gap. Agent definitions register only at session start, so a newly added agent can't be called in the session that created it.
