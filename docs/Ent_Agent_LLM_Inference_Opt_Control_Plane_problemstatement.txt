PROBLEM STATEMENT
================

PROJECT TITLE
-------------
Enterprise Agent & LLM Inference Optimization Control Plane


1. EXECUTIVE PURPOSE
--------------------
Build a production-ready, enterprise-grade optimization control plane for
LLM-powered applications, autonomous agents, developer/coding agents,
and multi-agent/sub-agent systems.

The framework shall reduce unnecessary inference cost, token consumption,
latency, context growth, redundant model/tool calls, and operational waste
while preserving:

- Correctness
- Semantic fidelity
- Retrieval relevance
- Output quality
- Security and tenant isolation
- Auditability
- Predictable behavior
- Reliability
- Model/provider portability

The framework must not be treated as a simple prompt-compression utility.
It shall be an adaptive, policy-driven optimization and governance control
plane that can sit between an AI application/agent orchestrator and one or
more LLM providers, and where supported can operate at the agent/tool and
inference-serving layers.

The central design principle is:

"Make tokens count instead of merely counting them."

The target product is an ENTERPRISE AGENT & LLM INFERENCE OPTIMIZATION
CONTROL PLANE. Its purpose is not to execute every optimization technique
on every request. It must continuously decide the cheapest safe execution
strategy that satisfies the required quality, latency, security, and
reliability constraints.

The framework shall optimize both:

1. TOKEN VOLUME
   Reduce tokens that need to be generated or processed.

2. TOKEN ECONOMICS
   Reduce the effective cost of processing tokens through caching, routing,
   batching, reuse, model selection, and conditional inference.

No optimization shall be considered successful solely because it reduces
token count. It must demonstrate acceptable quality and measurable net value.

Clarified by the Architecture Hardening Pass of 2026-09-15: "tokens" and
"inference" optimization are not one undifferentiated activity. The
framework distinguishes prompt/input token optimization, output/reasoning
token optimization, context optimization (retrieval, ranking, pruning,
dedup, reordering, budgeting), cache optimization, model/provider routing,
and inference-runtime optimization (Layer 3, Section 42) as separate
categories with separate ownership boundaries — the Control Plane owns and
directly implements the first five; for inference-runtime optimization it
owns awareness, integration, routing, and policy, while implementation
remains with model-serving infrastructure/providers. See Section 52.18.

The framework is also not the sole owner of every decision or every side
effect it touches. It may act as an advisor (recommend without enforcing),
an enforcer (block/require/rewrite within its policy authority), or an
execution owner (directly perform an action), and these are distinct roles
that must not be conflated. See Section 52.2. Nor does the framework
replace the agent orchestrator, IDE, or model-runtime infrastructure it
integrates with — see Section 52.20 for explicit anti-scope boundaries.


2. PROBLEM DEFINITION
---------------------
Modern LLM applications frequently send much more information to models than
the user-visible request suggests.

A single request can contain:

- System instructions
- Developer instructions
- User prompt
- Conversation history
- Retrieved RAG chunks
- Search results
- Policies and documentation
- Tool definitions
- Tool outputs
- API responses
- Logs
- Code
- Test output
- Previous agent plans
- Previous agent responses
- Intermediate reasoning/task state
- Repeated instructions
- Duplicated documents or excerpts

In agentic workflows, this context may be transmitted repeatedly across
multiple model calls.

The resulting problem is not simply "large prompts". It is uncontrolled
inference consumption caused by unnecessary, duplicated, stale, low-value,
poorly positioned, or repeatedly processed information.

The framework must therefore answer:

- What information is actually required?
- Which information can be removed?
- Which information can be compressed?
- Which information can be reused?
- Which information should be cached?
- Which model should process the request?
- How much reasoning is required?
- How much context is required?
- When should an agent stop?
- How much output is actually required?
- What is the cheapest safe way to satisfy the task?
- What quality was preserved after optimization?


3. ENTERPRISE OBJECTIVES
------------------------
The framework shall achieve the following strategic objectives.

OBJ-001: Reduce unnecessary input tokens.

OBJ-002: Reduce unnecessary output tokens.

OBJ-003: Bound conversation and context growth.

OBJ-004: Reduce redundant context propagation across agentic steps.

OBJ-005: Reduce unnecessary model calls.

OBJ-006: Reduce unnecessary tool calls and tool-output tokens.

OBJ-007: Reuse previously processed prompts, context, tool results, and
         semantically equivalent responses where safe.

OBJ-008: Route requests to the least expensive model capable of satisfying
         the quality requirement.

OBJ-009: Dynamically allocate token/reasoning budgets according to task
         complexity.

OBJ-010: Stop agentic workflows as soon as the objective has been
         sufficiently satisfied.

OBJ-011: Produce an auditable token and cost ledger for every optimized
         request.

OBJ-012: Provide organization-specific benchmark evidence before production
         rollout.

OBJ-013: Support multiple LLM providers and model families through a
         provider-neutral abstraction layer.

OBJ-014: Preserve security, privacy, authorization, and tenant boundaries
         while optimizing.

The following objectives were added by the Architecture Hardening Pass of
2026-09-15 (see Section 52 for full normative detail):

OBJ-023: Support synchronous, asynchronous/precomputed, and hybrid Control
         Plane operating modes, and treat Control Plane decision latency and
         compute overhead itself as part of the optimization problem.

OBJ-024: Distinguish advisory, enforcement, and execution/side-effect-owning
         decisions, and never assume the Control Plane owns agent planning or
         side effects unless explicitly integrated to do so.

OBJ-025: Bound the Control Plane's own latency, cost, and resource
         consumption, with backpressure, overload protection, and a
         deterministic safe fallback when those bounds are exceeded.

OBJ-026: Compute optimization value as verified net benefit across tokens,
         inference cost, optimization overhead, retrieval/routing/cache
         overhead, added latency, retries, quality degradation, and
         downstream/tool cost — never as token count alone.

OBJ-027: Enforce tenant/org/user/application spend budgets and runaway-cost
         protection without allowing budget logic to bypass security,
         authorization, or policy enforcement.

OBJ-028: Treat verifier output as calibrated evidence with a confidence
         score and acceptance threshold, never as unconditional ground truth.

OBJ-029: Classify, protect, and propagate deletion/retention decisions for
         sensitive data across every cache, memory, log, and trace surface
         the Control Plane touches.

OBJ-030: Declare an explicit integration feasibility tier for every
         coding-agent integration rather than assuming complete interception.

OBJ-031: Preserve Control Plane execution truth, authorization state, policy
         state, and context/workflow version as authoritative over any
         agent-owned working memory, with explicit conflict resolution.

OBJ-032: Account for concurrent mutation, staleness, and version conflict
         across multiple agents, sub-agents, and workflows sharing resources,
         with reconciliation, coordination, and idempotency guarantees.

OBJ-033: Require explicit human approval for designated consequential or
         irreversible actions, selected by policy/risk rather than applied
         to every action.

OBJ-034: Treat prompt injection and malicious or mutated retrieved/tool/
         context content as a security concern that is screened before any
         optimization stage may admit or act on that content.

OBJ-035: Maintain clear anti-scope boundaries distinguishing what the
         Control Plane builds from what it integrates with (agent
         orchestrators, model-training systems, model-runtime
         infrastructure, provider infrastructure, developer IDEs).


4. PRODUCT SCOPE: MULTI-MODE LLM AND AGENT OPTIMIZATION
-----------------------------------------------------------
Developer/coding-agent optimization is a FIRST-CLASS PRODUCT REQUIREMENT.
It is not an optional use case.

The framework shall support four primary execution environments through one common optimization engine:

A. GENERIC LLM APPLICATIONS
B. AUTONOMOUS / TOOL-USING AGENTS
C. DEVELOPER / CODING AGENTS (Cursor, Claude Code, GitHub Copilot, Antigravity, Codex, and comparable platforms, subject to available integration surfaces)
D. MULTI-AGENT / SUB-AGENT SYSTEMS

The product shall use a common optimization core with integration adapters, not a separate optimizer for every agent product. It shall optimize every model-bound context generated by an agent, not merely the original user prompt.

INTEGRATION MODES
-----------------
1. API / LLM Gateway Proxy
2. SDK / Middleware integration
3. MCP-based optimization services
4. Agent-harness integration for controllable/open implementations
5. Provider/platform enterprise integrations where supported

These integration modes do not imply that every target application, agent,
or coding-agent platform grants the same depth of access. Coding-agent
integrations in particular shall be classified by feasibility tier
(deep/native, gateway/interception, plugin/extension, protocol/tool-level,
or advisory/observability-only) rather than assuming complete request
interception is always available. See Section 52.8 for the full
requirement; the exact mechanism per platform remains an architecture
decision, not a problem-statement commitment.

The adapter layer shall normalize different agent/provider interfaces into a common representation: AgentRequest, AgentContext, InstructionContext, RepositoryContext, ToolContext, RetrievalContext, ConversationContext, MemoryContext, AgentState, ModelPolicy, and OptimizationPolicy.

DEVELOPER-AGENT OPTIMIZATION MODULES
------------------------------------
DA-001 CODE-AWARE CONTEXT PRUNER — remove low-value code context while preserving task-critical dependencies.

DA-002 SYMBOL-LEVEL CONTEXT SELECTOR — select relevant functions, methods, classes, interfaces, types, imports, callers, callees, references, and surrounding code instead of whole files where possible.

DA-003 REPOSITORY MAP GENERATOR AND CACHE — maintain a compact repository structure and reuse it instead of repeatedly rediscovering the codebase.

DA-004 GIT-DIFF OPTIMIZER — summarize large diffs and expose detailed changed sections selectively.

DA-005 TERMINAL OUTPUT OPTIMIZER — filter, summarize, structure, and deduplicate large terminal outputs.

DA-006 COMPILER / TEST / LINTER ERROR EXTRACTOR — extract actionable failures, locations, stack traces, expected/actual values, and relevant context from noisy output.

DA-007 DYNAMIC MCP / TOOL SELECTOR — expose only MCP tools/resources/capabilities relevant to the current task where supported.

DA-008 TOOL SCHEMA OPTIMIZER — minimize unnecessary tool-definition context while preserving invocation semantics, constraints, authorization, and parameters.

DA-009 SUB-AGENT RESULT COMPRESSOR — convert verbose sub-agent results into compact structured findings while retaining evidence, locations, confidence, unresolved questions, and recommendations.

DA-010 AGENT MEMORY OPTIMIZER — separate short-term task state from durable project/task memory and retain only useful information.

DA-011 CODE-AWARE SEMANTIC DEDUPLICATOR — detect duplicate/equivalent code, stack traces, errors, files, search results, diffs, and findings.

DA-012 ERROR-DRIVEN CONTEXT RETRIEVAL — use compiler/test/runtime errors and source locations to drive targeted retrieval.

DA-013 DEVELOPER-AGENT CONTEXT BUDGET MANAGER — dynamically allocate budgets across repository, conversation, tools, MCP, memory, search results, terminal output, and agent state.

DA-014 AGENT LOOP COST / TOKEN CONTROLLER — track cumulative cost of reasoning-tool-reasoning cycles and stop low-value loops.

DA-015 CODE CONTEXT REORDERER — optimize ordering of code, instructions, errors, tests, and evidence while preserving instruction precedence.

DA-016 FILE-SECTION LAZY LOADER — prefer metadata, signatures, symbol summaries, and targeted sections before loading complete files.

DA-017 REPOSITORY SEARCH RESULT OPTIMIZER — rank and deduplicate code-search results and return the smallest useful set.

DA-018 AGENT PLAN CONTEXT OPTIMIZER — retain active plan state, decisions, milestones, and unresolved work instead of full planning history.

DA-019 CODE EDIT CONTEXT OPTIMIZER — provide the smallest safe context required for a correct patch while preserving interfaces, dependencies, tests, and formatting constraints.

DA-020 DEVELOPER-AGENT OUTPUT CONTROLLER — bound verbose explanations, patches, summaries, and machine-readable outputs without harming correctness.

DA-021 AGENT TASK COMPLETION / EARLY-EXIT CONTROLLER — prevent unnecessary searches, model calls, tests, and tool loops after sufficient completion.

DA-022 DEVELOPER-AGENT CACHE LAYER — support exact, semantic, repository-aware, tool-result, search-result, repository-map, and stable-context caching with freshness and authorization controls.

DA-023 CONTEXT PROVENANCE TRACKER — record the origin of retained context such as file/path/line, tool, search, sub-agent, conversation turn, or memory.

DA-024 CONTEXT INVALIDATION ENGINE — invalidate repository/search/tool/memory caches when files, branches, dependencies, permissions, or external state change.

DA-025 PATCH / CHANGE IMPACT ANALYZER — estimate affected files, symbols, tests, and dependencies and prioritize relevant context.

DEVELOPER-AGENT MODEL-BOUND PIPELINE
-------------------------------------
Developer Request
 -> Agent Context Construction
 -> Context Adapter/Interception
 -> Task + Complexity Analysis
 -> Repository Map / Memory Lookup
 -> Dynamic Tool + MCP Selection
 -> Error-Driven / Symbol-Aware Retrieval
 -> Search Result Ranking
 -> Code-Aware Context Pruning
 -> Deduplication
 -> Terminal/Test/Linter Output Optimization
 -> Sub-Agent Result Compression
 -> Context Ranking
 -> Context Budget Allocation
 -> Context Compression
 -> Context Reordering
 -> Cache-Aware Prompt Assembly
 -> Model Routing
 -> Reasoning Budget Selection
 -> LLM
 -> Output Validation
 -> Tool / File / Patch Action
 -> Tool-Result Optimization
 -> Agent Loop Controller
 -> Repeat only when additional work has sufficient expected value
 -> Final Result

The framework must optimize every model-bound iteration, not only the first user request.

DEVELOPER-AGENT SUCCESS METRICS
-------------------------------
Measure tokens per coding task/iteration/tool call/test-debug cycle; repository/code/terminal/MCP/sub-agent/memory/history/diff tokens; model and tool calls per completed task; agent iterations; files inspected; relevant-vs-irrelevant context ratio; cache hit rate; early-exit rate; task completion; patch correctness; test pass rate; regression rate; developer acceptance; and cost per successfully completed coding task.

A coding-agent optimization is successful only when it reduces net inference cost and/or latency without materially degrading patch correctness, test success, task completion, security, or developer experience.

6. CORE COMPONENTS AND REQUIREMENTS
-----------------------------------


6.1 T0.1 MODEL ROUTER
---------------------
Purpose:
Select the least expensive model that can satisfy the task's required
quality, capability, latency, and compliance constraints.

Requirements:
- Support configurable model tiers.
- Consider task intent and complexity.
- Consider historical quality.
- Consider model price.
- Consider latency requirements.
- Consider context-window requirements.
- Consider tool/function support.
- Consider provider availability.
- Support deterministic rules initially.
- Support learned routing as an optional advanced capability.
- Support automatic escalation to a stronger model when confidence/quality
  is insufficient.

The router must not optimize cost by routing safety-critical or complex
requests to incapable models.

Research basis:
RouteLLM demonstrates model routing as a cost/quality trade-off and reports
substantial cost reduction in its evaluated settings.


6.2 T0.2 TASK / COMPLEXITY ANALYZER
-----------------------------------
Determine an approximate task complexity before expensive inference.

Possible signals:
- Intent
- Input size
- Number of entities
- Number of required operations
- Number of tools required
- Retrieval depth
- Historical task complexity
- Expected output structure
- Need for reasoning
- Confidence requirements

Output:
- Complexity class
- Recommended model tier
- Recommended context budget
- Recommended reasoning budget
- Recommended output budget


6.3 T0.3 REASONING BUDGET CONTROLLER
------------------------------------
Not every request requires the same amount of reasoning.

The controller shall dynamically select a reasoning budget based on task
complexity.

Example:

Simple extraction
    -> low reasoning budget

Moderate analysis
    -> medium reasoning budget

Complex multi-step reasoning
    -> high reasoning budget

Requirements:
- Support model/provider-specific reasoning controls where available.
- Never reduce reasoning solely to meet a token target.
- Compare quality against baseline.
- Support configurable minimum quality thresholds.
- Record allocated and consumed reasoning tokens where the provider exposes
  them.
- Support fallback escalation when the initial reasoning budget is
  insufficient.


6.4 T1.1 SANITIZER
------------------
Normalize raw input before downstream processing.

Capabilities:
- Normalize whitespace.
- Remove irrelevant formatting.
- Remove duplicated content.
- Strip known UI noise.
- Normalize equivalent representations.
- Preserve code, structured data, identifiers, URLs, and user-intent
  information.
- Produce baseline token count.
- Produce post-sanitization token count.

The sanitizer must be content-aware and must not blindly remove syntax that
is meaningful to the task.


6.5 T1.2 INTENT CLASSIFIER
--------------------------
Minimum supported intents:

- Factual
- Comparative
- Procedural
- Summarization
- Extraction
- Classification
- Coding
- Debugging
- Retrieval
- Open-ended
- Agentic workflow

The classifier shall select downstream policies including:
- Prompt template
- Retrieval strategy
- Context budget
- Output schema
- Model tier
- Reasoning budget
- Compression strategy


6.6 T1.3 ENTITY EXTRACTION
--------------------------
Extract structured information before downstream retrieval/model execution.

Examples:
- Named entities
- Numeric values
- Dates
- Date ranges
- Product identifiers
- Customer identifiers
- Categories
- Geographic constraints
- Filters

Entity metadata shall be available to:
- Retrieval
- Tool calls
- Ranking
- Prompt assembly
- Validation

This reduces the need for downstream models to repeatedly perform basic
information extraction.


6.7 T1.6 PROMPT CACHE
---------------------
Purpose:
Avoid repeatedly processing identical cacheable prompt prefixes.

Cache candidates:
- System instructions
- Developer instructions
- Tool definitions
- Few-shot examples
- Stable policy content
- Stable documentation
- Stable conversation prefixes

Requirements:
- Exact-match cache semantics by default.
- Configurable TTL.
- Tenant/workspace isolation.
- Permission-aware cache keys.
- Model/version-aware cache keys.
- Provider-aware cache abstraction.
- Cache hit/miss measurement.
- Cache write/read accounting.
- Cache invalidation.
- No cross-tenant leakage.
- No caching of content prohibited by policy.

The Prompt Assembler shall intentionally construct cache-stable prefixes.

Prompt caching is supported by major providers and can reduce processing
cost and latency for repeated prompt prefixes. Anthropic's current
documentation, for example, describes automatic and explicit prefix caching,
TTL controls, cache reads/writes, and cache isolation. The implementation
must remain provider-neutral because cache semantics differ by provider.


6.8 T1.7 SEMANTIC CACHE
-----------------------
Purpose:
Reuse results for semantically equivalent or sufficiently similar requests.

Requirements:
- Semantic similarity detection.
- Configurable similarity threshold.
- TTL.
- Data freshness validation.
- Tenant/user authorization checks.
- Source/version checks.
- Model/version compatibility checks.
- Tool-state compatibility checks.
- Explicit invalidation for mutable data.
- Ability to bypass cache for time-sensitive queries.

The system shall distinguish:
- Exact cache hit
- Semantic cache hit
- Unsafe/invalid cache candidate
- Cache miss

Semantic caching must never return a stale or unauthorized result merely
because the query is similar.


6.9 T1.9 CONTEXT PRUNER
-----------------------
Purpose:
Remove low-value context before expensive compression or inference.

Techniques may include:
- Sentence-level relevance
- Paragraph-level relevance
- Embedding similarity
- Lexical similarity
- Entity overlap
- Metadata filtering
- Recency
- Source authority
- Task-specific rules

The pruning stage should be primarily deterministic or lightweight.

The system must measure:
- Tokens before pruning
- Tokens after pruning
- Information/quality impact
- False-pruning rate


6.10 T1.10 CONTEXT DEDUPLICATOR
-------------------------------
Detect and remove duplicate or near-duplicate information across:

- Conversation history
- RAG chunks
- Tool results
- Uploaded documents
- Search results
- Previous agent outputs
- Code and logs

Supported levels:
- Exact duplicate detection
- Near-duplicate detection
- Paragraph-level duplicate detection
- Code duplicate detection
- Repeated tool-output detection

The system shall preserve one canonical copy and record removed tokens.


6.11 TOKEN-AWARE RANKER
-----------------------
Rank context using more than relevance alone.

The ranking strategy should consider:

- Relevance
- Recency
- Information density
- Token cost
- Source authority
- Diversity
- Duplication
- Task importance

A conceptual utility function is:

Utility =
    Relevance
    × Information Density
    × Authority
    × Diversity
    ÷ Token Cost

The exact formula shall be benchmarked rather than assumed to be universally
optimal.


6.12 ADAPTIVE RETRIEVAL / TOP-K
-------------------------------
Do not always retrieve a fixed number of chunks.

The system shall support dynamic K based on:
- Query complexity
- Relevance scores
- Confidence
- Token budget
- Information coverage
- Redundancy

Example:
- Simple query -> 2 chunks
- Normal query -> 4 chunks
- Complex query -> 8 chunks

The framework must compare adaptive retrieval against fixed-K baselines.

More retrieved context must not automatically be considered better.


6.13 T1.8 CONTEXT COMPRESSOR
----------------------------
Compress retrieved/contextual material while preserving task-relevant
information.

The compressor shall support:
- Extractive compression
- Model-based compression
- Query-aware compression
- Coarse-to-fine compression
- Dynamic compression ratios
- Entity preservation
- Subsequence/sentence recovery
- Code-aware preservation where required

The system shall support multiple compression strategies and select among
them according to context size, task type, quality risk, and cost.

Research basis:
LLMLingua presents coarse-to-fine prompt compression with budget control.
LongLLMLingua adds question-aware compression, document reordering, dynamic
compression ratios, and subsequence recovery for long-context scenarios.
LLMLingua-2 treats compression as token classification and reports faster
compression than earlier approaches in its evaluated settings.

Reported research numbers are benchmark results, not guaranteed production
targets. The framework must validate compression against its own workloads.


6.14 T1.11 CONTEXT REORDERER
----------------------------
After selecting context, optimize its ordering.

Requirements:
- Place highest-value information in strategically useful positions.
- Keep user query and task instructions clearly identifiable.
- Preserve source boundaries.
- Avoid accidental instruction precedence changes.
- Support model-specific ordering policies.
- Measure quality before and after reordering.

The framework shall specifically evaluate the effect of "lost in the
middle"/position bias.

LongLLMLingua includes document reordering as part of its long-context
compression approach.


6.15 T1.5 SOFT RESET / CONTEXT BUDGETER
---------------------------------------
Maintain a hard or configurable context ceiling.

Default reference budget:
500K tokens, based on the source whitepaper.

The budget must be configurable by:
- Model
- Provider
- Workflow
- Tenant
- User
- Intent
- Task complexity

When the context exceeds its budget:
1. Rank context.
2. Remove low-value context.
3. Deduplicate.
4. Compress remaining context if required.
5. Summarize older history where appropriate.
6. Preserve key facts and decisions.
7. Record a reset report.

The system must not assume that a larger context window is always beneficial.


6.16 T2.1 QUERY COMPRESSOR
--------------------------
Compress the user's request while preserving functional equivalence.

Remove:
- Repetition
- Filler
- Unnecessary politeness
- Redundant explanations
- Duplicate instructions

Preserve:
- Intent
- Constraints
- Entities
- Numbers
- Dates
- Exceptions
- Required output format
- Safety/security requirements

The original request must remain available for audit, evaluation, and fallback.

The source whitepaper cites typical 30–60% query reduction depending on
verbosity. This shall be treated as a validation target, not a guarantee.


6.17 PROMPT ASSEMBLER
--------------------
Build a final prompt that contains only the information needed for the
current task.

The assembler shall:
- Select intent-specific instructions.
- Include only approved context.
- Preserve required security/policy instructions.
- Maintain cache-stable prefixes.
- Add dynamic content after stable prefixes where possible.
- Produce final token counts.
- Produce a complete assembly ledger.

The assembler shall explicitly separate:

CACHEABLE PREFIX
- System instructions
- Stable developer policy
- Tool definitions
- Stable examples
- Stable reference material

DYNAMIC SUFFIX
- Current user request
- Current retrieved context
- Current tool results
- Current task state


6.18 OUTPUT SCHEMA SELECTOR
---------------------------
Select output structure based on intent.

Examples:

Factual:
- answer
- confidence
- source

Comparative:
- comparison table
- summary

Procedural:
- ordered steps
- bounded explanation

Extraction:
- strict structured schema

Coding:
- required code artifact
- bounded explanation

Agent/tool:
- machine-readable action/result structure


6.19 OUTPUT LENGTH CONTROLLER
-----------------------------
Apply field-level token budgets.

Examples:
- Maximum explanation length
- Maximum summary length
- Maximum number of steps
- Maximum number of returned records
- Maximum justification length

Where supported:
- max output tokens
- structured output
- JSON schema
- function calling
- grammar constraints
- stop sequences

If truncation occurs:
- Prefer semantic boundaries.
- Mark truncation.
- Preserve machine-readable validity where possible.
- Permit controlled expansion.


6.20 T3.1 AGENT STOP CONTROLLER
-------------------------------
Prevent unnecessary continuation of agentic workflows.

After each meaningful step, evaluate:

- Has the objective been satisfied?
- Is the result valid?
- Does the result meet quality thresholds?
- Are remaining steps necessary?
- Would another tool/model call materially improve the result?

If sufficient:
STOP.

The controller shall record:
- Planned steps
- Executed steps
- Skipped steps
- Early-termination reason
- Tokens saved
- Tool calls avoided
- Model calls avoided

This component directly targets agentic token explosion.


6.21 T3.2 TOOL OUTPUT FILTER
----------------------------
Tool outputs must not automatically be passed in full to the next LLM.

The filter shall:
- Select required fields.
- Remove metadata not required by the task.
- Remove debug information unless requested.
- Remove duplicate content.
- Compress large textual results.
- Enforce schemas.
- Apply token budgets.

Example:

Raw tool output:
    10,000 tokens

Required agent context:
    1,200 tokens

The system should pass the 1,200-token representation while retaining the
original result for audit where policy permits.


6.22 T3.3 TOOL RESULT CACHE
---------------------------
Cache deterministic or sufficiently stable tool results.

Candidate tools:
- Search
- Documentation retrieval
- Database queries
- Repository metadata
- File metadata
- External APIs
- Repeated calculations

Requirements:
- Tool-specific cache policy
- TTL
- Parameter normalization
- Authorization-aware cache keys
- Freshness policy
- Explicit invalidation
- Cache hit/miss accounting


6.23 MODEL CASCADE / ESCALATION
-------------------------------
Implement optional cascade execution:

1. Start with a lower-cost model.
2. Evaluate confidence/quality.
3. If acceptable, return.
4. Otherwise escalate to a stronger model.

Escalation may be triggered by:
- Low confidence
- Schema failure
- Validation failure
- Retrieval uncertainty
- User-defined quality requirements
- Safety/policy requirements
- Complexity threshold

Research basis:
FrugalGPT explores cascades and cost-aware combinations of LLMs. Such
research supports validation of the concept but does not guarantee the same
savings for every workload.


6.24 BATCH / ASYNCHRONOUS OPTIMIZER
-----------------------------------
Separate interactive and non-interactive workloads.

Interactive:
- prioritize latency

Asynchronous:
- prioritize cost efficiency
- batch compatible requests
- schedule offline workloads
- process bulk extraction/classification/summarization together

The framework shall distinguish:
- token reduction
- price-per-token reduction
- latency reduction
- throughput improvement

Batching must not be used where freshness or interactive latency makes it
inappropriate.

SEC-001:

SEC-005:

SEC-009:

SEC-010:
Provider-specific caching must not silently weaken organizational
security requirements.

The following requirements were added by the Architecture Hardening Pass
of 2026-09-15 (see Section 52 for full normative detail):

SEC-011:
Spend limits, circuit breakers, and budget-aware routing/execution must
never be used to bypass or substitute for authorization, policy, or
security enforcement. A budget decision and a security decision are
evaluated independently, and a passing budget check never implies a
passing security check.

SEC-012:
Sensitive data (including PII/PHI/PCI/secrets where applicable to the
deployment) must be classified before it is admitted to any optimization
stage, and classification must determine encryption, retention, and
caching eligibility. No specific regulatory regime is assumed to apply
unless the deployment's own scope/jurisdiction establishes it.

SEC-013:
Deletion or erasure of a data subject's data must propagate to every
surface the Control Plane persisted it to, including caches (exact and
semantic), agent/session memory, cost/token ledgers where they retain
content, and logs/traces — not only the primary store.

SEC-014:
Tool and MCP metadata (identity, capability declarations, schemas,
versions) are part of the security/control boundary. They must be
authenticated, authorization-checked, and validated for staleness and
integrity before being trusted; a tool result must not be treated as safe
solely because the tool call was authorized.

SEC-015:
Consequential or irreversible actions designated by policy or risk
classification must receive explicit human approval before execution.
This applies only to the designated subset of actions — not to every
action the Control Plane advises or enforces.

SEC-016:
Retrieved content, tool output, and other externally-sourced context are
untrusted by default and must pass prompt-injection and content-integrity
screening before any optimization stage (admission, ranking, compression,
caching, or tool/action authorization) is permitted to act on them.


11. FAILURE AND FALLBACK MODEL
------------------------------
Every optimization stage must have an explicit fallback.

If:
- Cache unavailable -> continue without cache.
- Semantic match uncertain -> cache miss.
- Sanitization fails -> use original input.
- Classification fails -> use safe general policy.
- Entity extraction fails -> use unstructured retrieval path.
- Ranking fails -> use bounded recent/relevance fallback.
- Pruning fails -> retain bounded original context.
- Compression fails -> use uncompressed context.
- Model routing fails -> use configured default model.
- Reasoning budget fails -> use safe default budget.
- Output schema fails -> use fallback validation/re-prompt.
- Agent stop decision fails -> continue only according to safe workflow policy.
- Token accounting fails -> mark usage as unverified; never fabricate savings.

Optimization failure must not become application failure unless the
optimization itself is explicitly required by policy.

17. RESEARCH-SUPPORTED TECHNIQUES

18. COST MODEL
--------------
The framework must support configurable pricing rather than hard-coded
prices.

Conceptual model:

Baseline Cost =
    Baseline Input Tokens × Input Rate
  + Baseline Output Tokens × Output Rate
  + Tool Costs
  + Other Provider Charges

Optimized Cost =
    Uncached Input Tokens × Input Rate
  + Cache Read/Write Cost
  + Compression Cost
  + Optimized Output Tokens × Output Rate
  + Tool Costs
  + Routing/Cascade Costs
  + Other Provider Charges

Net Savings =
    Baseline Cost - Optimized Cost

Savings % =
    Net Savings / Baseline Cost × 100

The system shall support provider-specific pricing dimensions because
different providers expose different cache, reasoning, batch, and token
pricing mechanisms.

25. ANTI-PATTERNS TO AVOID
--------------------------
The implementation must avoid:

- Compressing everything indiscriminately.
- Sending every retrieved chunk to the LLM.
- Using a fixed Top-K for every query.
- Always using the strongest/most expensive model.
- Always using the cheapest model.
- Passing complete tool responses to agents.
- Repeating the same system instructions unnecessarily.
- Carrying complete conversation history indefinitely.
- Re-running completed agent steps.
- Using semantic cache without freshness/authorization checks.
- Claiming savings without accounting for optimization overhead.
- Optimizing token count at the expense of correctness.
- Treating research benchmark percentages as guaranteed production savings.

Added by the Architecture Hardening Pass of 2026-09-15 (see Section 52.20):

- Building the Control Plane as a replacement agent orchestrator, a
  model-training system, model-runtime infrastructure, provider
  infrastructure, a general-purpose developer IDE, or a UX replacement for
  coding agents, instead of integrating with those systems.
- Assuming a coding-agent integration provides complete request
  interception when only a partial or observability-only integration tier
  is actually available.
- Treating a verifier's pass/fail output as ground truth without a
  calibrated confidence score and acceptance threshold.
- Allowing agent-owned working memory to override Control Plane execution
  state, authorization state, policy state, or context/workflow version.
- Admitting retrieved, tool, or other externally-sourced content into an
  optimization stage before it has passed prompt-injection/content-
  integrity screening.
- Allowing the Control Plane's own latency, compute, or cost overhead to
  exceed the value of the optimization it enables.

- Which model should execute?
- How much reasoning should be allocated?
- What output budget is required?
- Should the workflow continue?
- Should the request escalate or terminate?

The engine shall be policy-driven, measurable, explainable, and capable of
reordering optimization stages when evidence shows that another order gives
better net value.

OI-002 COST-OF-OPTIMIZATION CONTROLLER
--------------------------------------
The optimizer must account for its own computational and financial overhead.

For every optimization decision, estimate:

Expected Net Value =
    Expected Inference Cost Avoided
  - Optimization Compute Cost
  - Additional Provider Cost
  - Additional Tool Cost
  - Additional Latency Cost
  - Expected Quality/Risk Cost

An optimization shall be skipped when its expected benefit is not
sufficient to justify its overhead.

This prevents the optimizer from spending more money than it saves.

OI-003 ADAPTIVE OPTIMIZATION DEPTH CONTROLLER
---------------------------------------------
Select optimization depth based on task complexity, context size,
expected value, latency requirements, and historical workload behavior.

Example:

LOW complexity:
- exact cache
- deterministic hygiene
- basic routing

MEDIUM complexity:
- retrieval optimization
- pruning
- deduplication
- compression
- routing

HIGH complexity:
- dependency-aware retrieval
- context graph analysis
- advanced compression
- multi-agent economics
- deeper quality validation
- iterative optimization

The system shall not perform expensive optimization on requests where
simple optimization is sufficient.

OI-004 CONTEXT UTILITY / ROI SCORER
-----------------------------------
Assign a utility score to each context item.

Candidate signals:
- Task relevance
- Information density
- Source authority
- Recency
- Freshness
- Dependency importance
- Diversity
- Historical usefulness
- Confidence
- Token cost

Conceptual score:

Context ROI =
    Context Utility / Context Cost

The exact formula must remain configurable and benchmark-driven.

OI-005 OUTCOME-BASED OPTIMIZATION ENGINE
----------------------------------------
Optimize for successful outcomes rather than token reduction alone.

Required metrics include:
- Cost per successful answer
- Cost per successfully completed workflow
- Cost per successfully resolved task
- Cost per successfully completed coding task
- Tokens per successful outcome
- Model/tool calls per successful outcome

A token reduction that lowers task success must not be considered a win.

34. CONTEXT LIFECYCLE INTELLIGENCE
==================================
CL-001 CONTEXT DEPENDENCY GRAPH
-------------------------------
Represent context as a dependency graph rather than a flat collection.

For developer agents, the graph may include:
- User request
- Files
- Symbols
- Functions
- Classes
- Imports
- Callers/callees
- Tests
- Git changes
- Errors
- Tools
- Agent decisions

The graph shall support:
- Targeted retrieval
- Dependency-aware pruning
- Change-impact analysis
- Cache invalidation
- Freshness evaluation
- Recovery of previously removed context

CL-002 CONTEXT FRESHNESS SCORING
--------------------------------
Every retrievable context item should carry, where available:
- Source
- Version
- Commit
- Branch
- Timestamp
- Last verification time
- Freshness status

Freshness shall influence ranking, caching, retrieval, and validation.

CL-003 DEPENDENCY-AWARE CACHE INVALIDATION
------------------------------------------
When a source item changes, invalidate or revalidate dependent cached
representations.

Examples:
- File changed -> invalidate symbol summaries
- Symbol changed -> invalidate dependent context
- Branch changed -> invalidate branch-specific cache
- Permission changed -> invalidate affected cache entries
- External data changed -> invalidate freshness-sensitive semantic cache

CL-004 REVERSIBLE OPTIMIZATION
------------------------------
Where practical, destructive context reduction must remain recoverable.

Every transformed item should record:
- Original source
- Transformation type
- Removed range/content reference
- Reason
- Confidence
- Recovery pointer
- Expiration/freshness metadata

If later evidence indicates that removed information is required, the
optimizer shall be able to retrieve it without reconstructing the original
request manually.

CL-005 PROGRESSIVE CONTEXT COMPACTION
-------------------------------------
Compaction shall be proactive and multi-stage.

Example policy:
- 0-40% budget: full fidelity
- 40-60%: deduplicate
- 60-70%: remove low-value content
- 70-80%: compress historical/secondary context
- 80-90%: aggressive selective loading
- 90%+: controlled session reset or phase transition

Thresholds must be configurable and model-specific.

CL-006 HIERARCHICAL MEMORY
--------------------------
Support separate memory layers:
- Current turn
- Current task
- Session
- Project/repository
- Organization
- Historical knowledge

Each layer shall have independent:
- Retention
- Freshness
- Compression
- Retrieval
- Token budget
- Invalidation policy

CL-007 SESSION PHASE MANAGEMENT
-------------------------------
Long-running tasks shall support explicit phases such as:
- Discovery
- Planning
- Implementation
- Testing
- Review
- Completion

Each phase may use different context, tool, model, reasoning, and memory
policies.

35. CACHE ECONOMICS AND CACHE-AWARE ASSEMBLY
============================================
CE-001 CACHE ECONOMICS ENGINE
-----------------------------
Caching decisions shall consider:

Expected Cache Benefit =
    Future Reuse Probability
  × Tokens Avoided
  × Effective Input Price

versus:

Cache Cost =
    Write Cost
  + Storage Cost
  + Invalidation Cost
  + Freshness Risk
  + Cache Miss/Break Risk

The engine shall choose:
- No cache
- Short-lived cache
- Long-lived cache
- Exact cache
- Semantic cache
- Provider-native cache
- Application-side cache

based on expected net value.

Provider documentation demonstrates that prompt caching can materially
reduce repeated-input cost and latency, but cache write/read prices, TTLs,
and semantics vary by provider. The control plane must therefore model
provider-specific cache economics rather than assuming one universal rule.

CE-002 CACHE-AWARE CONTEXT CONSTRUCTION
---------------------------------------
The prompt assembler shall deliberately maximize reusable prefixes.

Preferred structure:

STABLE / CACHEABLE PREFIX
- System instructions
- Stable developer policies
- Stable tool schemas
- Stable project rules
- Stable examples
- Stable repository metadata

SEMI-STABLE REGION
- Project documentation
- Memory
- Slowly changing context

VOLATILE REGION
- Current user request
- Current files
- Current errors
- Current tool results
- Current task state

The optimizer shall minimize unnecessary changes to cacheable prefixes.

CE-003 CACHE FRAGMENTATION DETECTOR
------------------------------------
Detect likely cache misses caused by:
- Dynamic timestamps
- Random identifiers
- Tool ordering
- Serialization changes
- Whitespace/format changes
- Dynamic metadata
- Changing system instructions
- Changing tool definitions
- Unstable context ordering

The system shall produce a cache-miss diagnosis and estimate the potential
recoverable cache value.

CE-004 CACHE PRE-WARMING POLICY
------------------------------
Where the provider supports it, allow pre-warming of high-value stable
prefixes when the expected reduction in first-request latency/cost justifies
the pre-warm cost.

CE-005 CACHE BREAKPOINT OPTIMIZER
---------------------------------
Where provider semantics permit multiple cache boundaries, choose cache
breakpoints based on context stability and expected reuse frequency.

36. TOOL EXECUTION OPTIMIZATION
================================
TE-001 TOOL CALL ROI PREDICTOR
------------------------------
Before executing a tool, estimate:

Expected Information Gain
/
Expected Tool Cost + Token Cost + Latency Cost

Skip or defer tool calls whose expected value is insufficient.

TE-002 TOOL ARGUMENT OPTIMIZER
------------------------------
Optimize tool requests before execution.

Capabilities:
- Narrow search scope
- Add relevant filters
- Restrict paths
- Restrict result count
- Request only required fields
- Normalize parameters
- Eliminate redundant arguments

The goal is to reduce unnecessary output before it enters the LLM context.

TE-003 DYNAMIC TOOL LOADING
---------------------------
When supported, do not expose large tool catalogs upfront.

Use:
Task
 -> Tool index/search
 -> Relevant tool discovery
 -> Minimal tool schemas
 -> Execution

This is especially important for large MCP/tool ecosystems.

TE-004 PROGRAMMATIC TOOL EXECUTION
----------------------------------
Where supported, collapse multiple independent or sequential tool calls
into a programmatic execution unit so intermediate results do not all need
to enter the model conversation history.

The framework shall benchmark:
- Traditional tool round trips
versus
- Programmatic/aggregated execution

TE-005 PARALLEL TOOL EXECUTION
------------------------------
Identify independent tool calls and execute them concurrently where:
- Dependencies permit
- Side effects are safe
- Provider/agent policies permit

TE-006 TOOL RESULT VALUE FILTER
-------------------------------
Do not automatically propagate the entire result.

Retain only:
- Required fields
- Relevant records
- Relevant errors
- Evidence
- Provenance
- Required authorization/audit fields

TE-007 TOOL RESULT RECOVERY
---------------------------
Large filtered results shall remain recoverable where policy permits.

37. AGENT LOOP AND MULTI-AGENT ECONOMICS
========================================
AL-001 AGENT LOOP PROGRESS METER
--------------------------------
Measure for each agent iteration:
- Input tokens
- Output tokens
- Tool cost
- New information gained
- State change
- Objective progress
- Errors introduced/resolved

AL-002 LOOP WASTE DETECTOR
--------------------------
Detect:
- Repeated searches
- Repeated tool calls
- Repeated reasoning over unchanged state
- Oscillation between states
- No-progress iterations
- Dead-end loops

Clarified by the Architecture Hardening Pass of 2026-09-15 (Section 52.10):
repeated iteration is not inherently waste. The same surface pattern
(repeated tool calls, repeated reasoning over similar state) may represent
productive incremental progress, legitimate reflection/self-correction, a
justified retry, or genuine oscillation/failure. The detector shall
classify iterations against expected task value and evidence of state
change or new information, not merely count or pattern-match iterations.
Optimization based on this signal targets expected-value-negative loops,
never iteration count as an end in itself.

AL-003 SUB-AGENT VALUE PREDICTOR
--------------------------------
Before spawning a sub-agent, estimate:

Expected Sub-Agent Value
/
Sub-Agent Cost

Include:
- Agent inference cost
- Context duplication cost
- Aggregation cost
- Parent ingestion cost
- Latency
- Coordination overhead

Do not spawn a sub-agent when the expected value is insufficient.

AL-004 SUB-AGENT SCHEDULER
--------------------------
For independent tasks:
- Identify parallelizable work
- Execute concurrently where safe
- Aggregate results compactly
- Avoid duplicated repository exploration

AL-005 SUB-AGENT HANDOFF COMPRESSION
------------------------------------
A sub-agent handoff shall preserve:
- Objective
- Findings
- Evidence
- Files/symbols
- Confidence
- Decisions
- Unresolved questions
- Recommended next actions

It shall not require replaying the full sub-agent transcript.

AL-006 AGENT TASK VALUE / EARLY EXIT
------------------------------------
Stop an agent when:
- Objective is satisfied
- Required validation passes
- Additional information has low expected value
- Additional model/tool calls are unlikely to change the outcome

Record the avoided work.

38. ADAPTIVE MODEL, REASONING, AND OUTPUT CONTROL

AR-001 MARGINAL-GAIN MODEL ROUTING

Routing should consider not only predicted difficulty but the expected

Marginal Model Value =
    Expected Quality Gain / Additional Cost

- Model behavior

- Coding

AR-004 VERIFIER-GUIDED ESCALATION

Candidate verifiers:

42. INFERENCE / SERVING OPTIMIZATION LAYER
==========================================
Where the deployment has access to model-serving infrastructure, the control

This layer is OPTIONAL and infrastructure-dependent.

Reframed by the Architecture Hardening Pass of 2026-09-15 (Section 52.17):
the Control Plane's role at this layer is awareness, integration, routing,
policy, and capability negotiation with infrastructure/providers — never
the implementation of model-runtime mechanisms. The Control Plane shall NOT
implement its own KV-cache engine, continuous-batching scheduler,
speculative-decoding mechanism, quantization pipeline, or prefill/decode
disaggregation. Where such mechanisms exist, they are owned and operated by
the inference-serving infrastructure or provider; the Control Plane
integrates with them.

Capabilities the Control Plane is AWARE OF and may ROUTE/NEGOTIATE against
(implemented by infrastructure/providers, not by the Control Plane):
- Prefix/KV-cache reuse
- KV-cache compression
- Continuous batching
- Request scheduling
- Prefill optimization
- Decode optimization
- Speculative decoding
- Quantization
- Model replica selection
- GPU utilization optimization
- Inference queue management

For each capability, the Control Plane's own responsibility is limited to:
- detecting whether the provider/infrastructure exposes it,
- selecting or routing requests to take advantage of it where doing so is
  net-beneficial and policy-compliant,
- negotiating capability parameters (e.g. batching eligibility, cache
  affinity hints) through the provider adapter, and
- measuring its effect, kept separate from Layer 1/2 measurement.

These techniques must remain separate from prompt/context optimization and
must be enabled only after workload-specific validation.

44. OPTIMIZATION FRONTIER AND OBJECTIVE FUNCTION
=================================================
The control plane shall optimize:

MINIMIZE:
    Total Safe Inference Cost

SUBJECT TO:
    Quality >= configured minimum
    Correctness >= configured minimum
    Security >= required policy
    Reliability >= configured SLO
    Freshness >= required threshold
    Latency <= configured maximum
    Compliance = satisfied
    Task completion = satisfied

The system should expose the resulting operating point as a
cost/quality/latency frontier.

The optimizer shall prefer a solution on the efficient frontier rather than
blindly maximizing any single metric.

Clarified by the Architecture Hardening Pass of 2026-09-15: this
objective/constraint formulation is a conceptual and heuristic decision
framework that guides policy design, cost accounting, and evaluation — not
a specification for a literal real-time mathematical optimizer or
constraint solver executed synchronously on every request. Individual
decisions (routing, caching, pruning, escalation) are made by policy rules,
heuristics, or learned models operating within this framework, at whichever
of the operating modes in Section 52.1 (synchronous, asynchronous/
precomputed, or hybrid) is appropriate for that decision.

48. ADDITIONAL ANTI-PATTERNS
============================
The implementation must also avoid:

- Running every optimization on every request.
- Using an expensive optimizer to save fewer tokens than the optimizer costs.
- Treating semantic similarity as sufficient proof of cache safety.
- Caching mutable/permission-sensitive data without validation.
- Optimizing context without considering delayed relevance.
- Spawning sub-agents without value/cost analysis.
- Executing tools without considering expected information gain.
- Exposing large tool catalogs when on-demand discovery is possible.
- Assuming larger context windows eliminate context-management problems.
- Treating a cache hit as a quality guarantee.
- Treating token reduction as equivalent to business value.
- Allowing learned policies to change production behavior without governance.
- Mixing inference-serving optimizations with prompt optimization without
  separate measurement.
- Removing context without provenance or recovery information where recovery
  is required.
- Using provider-specific behavior as a universal architectural assumption.

51. DYNAMIC EXECUTION STATE & CONTEXT LIFECYCLE MANAGEMENT
----------------------------------------------------------
(Hardening Amendment — added 2026-09-10)

51.1 FOUNDATIONAL REQUIREMENT: STATEFUL EXECUTION
--------------------------------------------------
The system must treat every execution as a versioned, stateful lifecycle
rather than a single immutable request/response transaction.

An execution begins when a request is admitted and ends only when a
terminal state (COMPLETED, FAILED, CANCELLED, SUPERSEDED, or EXPIRED)
is committed to the audit record.  Between admission and terminal state,
the following entities may mutate:

  - Context (tokens added, removed, compressed, reordered, pruned)
  - Workflow (steps added, removed, reordered, paused)
  - Permissions (user role changed, token revoked, scope reduced)
  - Policy (optimization policy hot-reloaded, security rule updated)
  - Model availability (provider outage, rate-limit activation,
    capability downgrade)
  - Resource budgets (token ceiling reduced, cost cap adjusted)
  - External state (tool outputs change, files are modified,
    knowledge base is updated)

Every mutation of these entities must be:
  (a) detected,
  (b) version-stamped,
  (c) assessed for impact on in-flight work,
  (d) reconciled with existing execution state before the next
      optimization decision is made.

The system must NEVER make an optimization decision using a stale
snapshot of context, policy, permissions, or resource state.


51.2 STATE OWNERSHIP MODEL
--------------------------
Execution state is owned across three distinct domains:

DOMAIN 1 — OPTIMIZATION CONTROL PLANE STATE
  - OptimizationPlan version
  - Pipeline stage completion status
  - ReversibilityRecord set
  - Token ledger (running balance)
  - Policy snapshot (pinned at ingress)
  - Quality gate results (per stage)

DOMAIN 2 — CONTEXT STATE
  - Logical Task Context (all information accumulated for the task,
    regardless of what fits in any one model window)
  - Model-Admitted Context (the subset actually submitted to inference
    at each step — a strict subset of Logical Task Context)
  - Context version sequence (monotonically increasing per mutation)
  - Dependency graph (describes inter-item relationships)
  - Provenance records (source, freshness, authorization scope)

DOMAIN 3 — WORKFLOW STATE
  - Current step index and step graph
  - Completed actions set (prevents re-execution)
  - Unresolved questions set (drives continuation)
  - Checkpoint registry
  - Sub-agent spawned / resolved set
  - Suspension markers


51.3 LOGICAL TASK CONTEXT VS MODEL-ADMITTED CONTEXT
----------------------------------------------------
The system must maintain a strict distinction:

LOGICAL TASK CONTEXT
  The complete set of information relevant to the current task.
  May be larger than any model's context window.
  Persists across all iterations of a multi-step workflow.
  Never discarded by a pruning or compression operation without
  an explicit eviction record and reversibility record.

MODEL-ADMITTED CONTEXT
  The subset of Logical Task Context submitted to the model in a
  single inference call.
  Assembled fresh for each inference call from the current
  Logical Task Context after applying pruning, compression,
  ranking, and budget constraints.
  Treated as ephemeral — it is reconstructed for each call.

Consequences:
  - Context pruning operates on Logical Task Context by evicting
    items from the logical set (with a reversibility record) —
    not by silently dropping them at assembly time.
  - A context overflow condition must trigger an explicit eviction
    protocol, not silent truncation.
  - Items evicted from Logical Task Context that are later found
    to be required for task completion must trigger a context
    expansion event.


51.4 CONTEXT OVERFLOW MANAGEMENT
---------------------------------
When Logical Task Context exceeds the configured ceiling:

MANDATORY PROTECTION TIERS
  Tier 0 — Immutable:  SEC instructions, safety constraints,
            audit-required fields.  May NEVER be evicted.
  Tier 1 — Protected:  Developer instructions, decisions,
            commitments, constraints, mandatory audit fields.
            May ONLY be evicted if the task is terminal.
  Tier 2 — High-value: Recent conversation turns, active agent
            plan, unresolved questions.  May be compressed but
            not evicted while the task is active.
  Tier 3 — Standard:   Retrieved context, tool outputs,
            history beyond the rolling window.  Subject to
            standard pruning and compression.
  Tier 4 — Evictable:  Redundant, stale, or low-relevance items.
            Evicted first.

EVICTION PROTOCOL
  1. Identify Tier 4 candidates via dependency analysis.
  2. Evict candidates that have no live dependents.
  3. If overflow persists: compress Tier 3 items.
  4. If overflow persists: compress Tier 2 items (never evict).
  5. If overflow persists after Tier 2 compression: return
     BUDGET_OVERFLOW with section-by-section breakdown.
  6. Never proceed to inference with silent truncation.

CONTEXT EXPANSION EVENTS
  When a previously evicted item is found necessary for the
  current step, the system must:
  (a) Raise a ContextExpansionRequest.
  (b) Evaluate cost and budget impact.
  (c) If budget permits: re-admit the item (with freshness
      validation if external).
  (d) If budget does not permit: suspend the workflow and surface
      an EXPANSION_BUDGET_EXCEEDED condition to the caller.


51.5 INTERRUPTION AND PARTIAL EXECUTION
----------------------------------------
A multi-step execution may be interrupted at any point by:
  - User cancellation
  - Timeout
  - Provider outage
  - Policy change that invalidates the current plan
  - Security event requiring immediate halt
  - Budget exhaustion

REQUIREMENTS FOR EACH INTERRUPTION CAUSE:

USER CANCELLATION
  - Record a CANCELLATION checkpoint immediately.
  - Complete the current atomic unit of work (a single model call
    or tool call) unless the cancellation is marked IMMEDIATE.
  - Return a PARTIAL result with the completion state at the
    point of cancellation.
  - Preserve the checkpoint for potential resume.

TIMEOUT
  - Record a TIMEOUT checkpoint with current state.
  - Return a PARTIAL result.
  - Mark work completed so far in the audit record.
  - Never report timed-out work as completed.

PROVIDER OUTAGE
  - Activate the circuit breaker.
  - Checkpoint current state.
  - Attempt failover to the next available model.
  - If failover unavailable: return PARTIAL with
    status = PROVIDER_UNAVAILABLE.

POLICY CHANGE
  - Pin the policy version at ingress.  Policy changes do NOT
    affect in-flight executions.
  - If an in-flight execution detects a security policy change
    that cannot be deferred: suspend, revalidate, then resume
    or cancel.

BUDGET EXHAUSTION
  - Return PARTIAL with remaining-budget = 0.
  - Never silently overspend the configured budget.
  - Provide a per-section breakdown of budget consumption.


51.6 CHECKPOINTING AND RESUMABILITY
-------------------------------------
Any multi-step workflow execution of 3 or more steps MUST support
checkpointing.

CHECKPOINT CONTENT
  - execution_id (immutable)
  - execution_version at checkpoint time
  - context_version at checkpoint time
  - workflow_version at checkpoint time
  - completed_actions (set)
  - unresolved_questions (set)
  - token_ledger_snapshot
  - policy_version at checkpoint time
  - model_selected at checkpoint time
  - reversibility_records written so far

RESUME SEMANTICS
  Resume operations must reconcile state and current intent.
  They must NOT blindly replay steps.

  On resume:
  1. Load the checkpoint.
  2. Re-validate permissions against current authorization state.
  3. Re-validate policy against current policy version.
  4. Re-validate model availability.
  5. Check completed_actions to avoid re-execution.
  6. Validate freshness of external context items.
  7. Reconcile: if the intended objective has been satisfied by
     completed actions, return the result without re-execution.
  8. Continue from the first unresolved step.

  If steps (2)–(6) fail: surface a RESUME_PRECONDITION_FAILED
  error with the specific failed precondition.


51.7 SUPERSESSION
-----------------
A supersession occurs when a new request makes an in-flight
execution obsolete.  Examples:

  - The user submits a revised version of the same task.
  - A background agent receives a more up-to-date instruction.
  - A workflow step is invalidated by an external state change.

SUPERSESSION REQUIREMENTS
  - The superseded execution must be marked SUPERSEDED in the
    audit record.
  - The new execution must receive a fresh execution_id.
  - Any shared context items must be re-validated for freshness
    before being admitted into the new execution.
  - Completed actions from the superseded execution must be
    surfaced to the new execution to avoid redundant re-work
    (but only after freshness validation).
  - Token and cost accounting for the superseded execution must
    be finalized and closed separately.


51.8 DYNAMIC PERMISSION AND POLICY CHANGES
-------------------------------------------
PERMISSION CHANGES DURING EXECUTION
  The system must treat permission changes as first-class events:

  (a) Cache entries (tool results, semantic cache, prompt cache)
      must be invalidated for the affected user/role upon any
      permission change that reduces access scope.
  (b) Tool executions that are in-flight when a permission change
      is received must be revalidated before their results are
      admitted to context.
  (c) Agent steps that depend on data the user can no longer
      access must be marked BLOCKED and surfaced to the caller.

POLICY HOT-RELOAD
  Optimization policy changes take effect on the NEXT admitted
  request.  Never mid-execution.

  Exception: security policy changes (SEC-001–010 domain) may
  force an in-flight suspension if the change increases a
  mandatory restriction.  In that case:
  (a) Suspend the execution.
  (b) Re-evaluate the in-flight plan against the new policy.
  (c) If the plan remains valid: resume.
  (d) If the plan is now policy-violating: cancel with
      POLICY_VIOLATION status.


51.9 STALE RESULT PROTECTION
-----------------------------
The system must reject or flag stale results in all of the
following cases:

  (a) A semantic cache hit whose freshness_valid = false for a
      time-sensitive query.
  (b) A tool result cache hit after the underlying data has
      changed.
  (c) A prompt cache hit after the policy_version has changed.
  (d) A resumed execution that contains context items whose
      external sources have been updated since checkpoint.
  (e) A sub-agent result that references files, symbols, or API
      responses that have changed since the sub-agent ran.

In every case:
  - The stale item must be re-fetched or re-executed.
  - The stale item must NOT be silently served.
  - The stale detection event must be logged.


51.10 FAIL-SAFE CLASSIFICATION
-------------------------------
The system applies two fail-safe modes:

FAIL-OPEN (optimization failures)
  If an optimization stage fails, the pipeline continues with
  the unoptimized content.  The failure is logged but does not
  become an application failure.

FAIL-CLOSED (security and integrity failures)
  If a security check, PII detection, authorization check,
  or mandatory audit record write fails, the request is rejected.
  The failure is logged as a security event.
  Under no circumstances may a security failure produce a silent
  pass-through.

The boundary between fail-open and fail-closed is governed by
the SEC-001–010 requirements and the Tier 0 immutability
requirement in Section 51.4.


51.11 SCENARIO VALIDATION AS FIRST-CLASS ENGINEERING PROCESS
-------------------------------------------------------------
Scenario completeness is a first-class engineering gate.  Before
any pipeline stage is declared production-ready, the following
must be verified:

NORMAL SCENARIOS
  - The full optimization pipeline executes end-to-end correctly.
  - All quality gates pass.
  - Token ledger balances.
  - Fallback paths do not activate unexpectedly.

ABNORMAL SCENARIOS (mandatory coverage)
  - Context overflow at each tier boundary.
  - Context expansion after eviction.
  - Interruption at each pipeline stage.
  - Permission change during execution.
  - Policy hot-reload during execution.
  - Provider outage at model routing, cascade, and retry.
  - Partial execution resume (checkpoint/resume).
  - Supersession during multi-step execution.
  - Stale result rejection at every cache type.
  - Dependency-cascade failure in context eviction.
  - Budget exhaustion at each section.
  - Adversarial injection through compressed context.
  - Cross-tenant isolation under concurrent load.
  - Loop detection and graceful loop-break.
  - Sub-agent handoff with oversized context.
  - Quality gate failure after optimization.
  - Optimization overhead inversion (pipeline costs exceed savings).
  - Policy violation detected at resume.

This list is minimum required coverage.  Additional scenarios
discovered during implementation must be added to the scenario
matrix before production approval.


51.12 RELATIONSHIP TO AGENT-OWNED MEMORY AND CROSS-EXECUTION SHARED STATE
---------------------------------------------------------------------------
(Added by the Architecture Hardening Pass of 2026-09-15.)

Sections 51.1-51.11 define execution truth for a single execution. Two
extensions are required and are specified normatively in Section 52:

  - An agent may maintain its own working memory (short-term task state,
    scratch reasoning, local caches). That memory is never authoritative
    over the execution state, authorization state, policy state, or
    context/workflow version owned under this section. See Section 52.9.

  - Multiple agents, sub-agents, or workflow executions may read or mutate
    shared resources (files, tickets, shared memory, external systems)
    concurrently. The single-execution reconciliation model in Sections
    51.1 and 51.7-51.9 extends to cross-execution concurrency, staleness,
    and idempotency. See Section 52.12.

    TRUST BOUNDARIES (2026-09-15)
========================================================================
This section is a controlled hardening pass over the baseline established
in Sections 1-51. It does not replace any preceding requirement. Where a
preceding section already addressed part of a concept below, this section
cross-references it and adds only what was missing; where a preceding
section's wording created ambiguity against a requirement below, the
relevant section was edited directly (see Sections 1, 4, 5, 10, 24, 25, 37,
42, 44, 48, 51 above) and this section states the resolution explicitly.

Twenty hardening requirements are addressed, one per subsection (52.1
through 52.20), corresponding to H01-H20 of the approved hardening
direction.


52.1 CONTROL PLANE OPERATING MODEL (H01)
-----------------------------------------
The Control Plane may operate in three modes, selectable per decision
type, not as a single global setting:

SYNCHRONOUS / REQUEST-PATH MODE
  The decision is made inline, in the critical path of the request it
  affects. Required when the decision depends on information that only
  exists at request time (the actual prompt, the actual retrieved
  context, the actual permission state) and cannot be safely precomputed.
  Examples: exact/semantic cache lookup, sanitization, context pruning for
  the current request, agent stop/continue evaluation.

ASYNCHRONOUS / PRECOMPUTED MODE
  The decision, or the inputs to it, are computed ahead of the request
  that will use them and looked up synchronously (or refreshed in the
  background) rather than recomputed per request. Appropriate when the
  underlying information changes slowly relative to request volume.
  Examples: provider/model optimization profiles (Section 41), repository
  maps (DA-003), cache pre-warming (CE-004), routing-policy compilation,
  pricing-table refresh, cache-fragmentation diagnosis (CE-003),
  optimization regression detection (EL-005).

HYBRID MODE
  A precomputed/cached artifact is consulted synchronously, but is
  revalidated or recomputed inline when a freshness check indicates it may
  be stale (see Section 51.9 Stale Result Protection), or when confidence
  in the precomputed artifact is below a policy threshold (see AR-004,
  Section 52.6). Most production decisions in this framework are expected
  to be hybrid: a fast synchronous lookup backed by an asynchronously
  maintained artifact, with a synchronous fallback path when the lookup is
  unusable.

REQUIREMENTS
  - The framework must not assume every optimization decision executes
    synchronously in the critical request path. Section 5's pipeline
    diagram and Section 9's developer-agent pipeline describe a logical
    decision sequence; they do not mandate synchronous execution for every
    stage on every request (see the note appended after the Section 5
    diagram).
  - Every optimization stage's specification must state which mode(s) it
    supports. Where a stage supports more than one mode, the choice of
    mode is itself a policy-driven decision subject to the same net-value
    accounting as any other optimization (Section 52.4).
  - Control Plane decision latency and compute overhead are themselves
    part of the optimization problem, not externalities. Choosing
    synchronous evaluation when a precomputed/hybrid alternative would
    achieve equivalent safety and quality at lower latency/cost is itself
    a form of the "expensive optimizer" anti-pattern (Section 48).
  - Precomputed/cached decisions are subject to the same staleness,
    versioning, and reconciliation requirements as any other cached
    artifact under Sections 51.8-51.9.

OBJ-023 (Section 3) is the objective anchor for this subsection.


52.2 ADVISOR, ENFORCER, AND EXECUTION-OWNER BOUNDARY (H02)
-------------------------------------------------------------
The Control Plane's relationship to any given decision or side effect
falls into exactly one of three categories, and the category must be
declared, not inferred:

ADVISORY
  The Control Plane recommends a course of action (a model choice, a
  context reduction, a cache reuse, a stop/continue signal) but the
  calling agent/application/workflow decides whether to act on it and
  performs any resulting action itself. The Control Plane owns no side
  effect in this mode.

ENFORCEMENT
  The Control Plane blocks, requires, rewrites, or gates a request or
  action within its policy authority (for example: rejecting a request
  that fails a security check, capping an output budget, refusing to
  admit unauthorized context). Enforcement changes what is allowed to
  happen, but the calling agent/application still performs the resulting
  action.

EXECUTION / SIDE-EFFECT OWNERSHIP
  The Control Plane itself performs an action with an external side
  effect (for example: writing to a cache, invoking a tool on the
  agent's behalf under a programmatic-execution integration such as
  TE-004, or committing a checkpoint). This is the only category in
  which the Control Plane is directly responsible for the side effect's
  correctness and reversibility.

RESPONSIBILITY BOUNDARY
  - Task planning, business logic, and the decision to perform an
    irreversible external action belong to the Agent/Workflow/External
    System by default. The Control Plane advises or enforces around that
    planning; it does not silently assume ownership of it.
  - Any component that crosses from advisory/enforcement into execution
    ownership (e.g., a programmatic tool-execution aggregator, an
    automatic cache write, an automatic checkpoint commit) must be
    identified as such, and inherits the reversibility, audit, and
    fail-safe-classification requirements of Sections 51.10 and 52.15 for
    that action.
  - A single request may involve all three categories at different
    pipeline stages (e.g., enforcement at the security gate, advisory at
    model routing, execution ownership at a tool-result cache write).
    Each decision's category must be recorded in the audit record
    (Section 52.15) independently.

OBJ-024 is the objective anchor for this subsection.


52.3 CONTROL PLANE SELF-PROTECTION (H03)
-------------------------------------------
The Control Plane is itself a system with latency, cost, and reliability
characteristics, and must protect itself using the same discipline it
applies to the applications it optimizes.

REQUIREMENTS
  - LATENCY BUDGET: every synchronous decision (Section 52.1) has a
    configurable maximum added latency. If a stage cannot complete within
    its budget, it must fail open per Section 51.10 (fall back to the
    unoptimized path) rather than block the request indefinitely.
  - PROCESSING / COST BUDGET: the Control Plane's own compute and
    provider-API usage (e.g., an LLM-based compressor or classifier) is
    metered and bounded per request and per tenant, and is included in
    the Optimization Compute Cost term in Section 52.4's net-benefit
    accounting.
  - BACKPRESSURE: under load, the Control Plane must shed optimization
    depth before it sheds correctness or security. The Adaptive
    Optimization Depth Controller (OI-003) is the primary mechanism for
    this; under sustained overload it must be able to step down to the
    LOW-complexity policy tier even for requests that would otherwise
    warrant deeper optimization.
  - OVERLOAD PROTECTION: the Control Plane must detect its own overload
    (queue depth, latency percentile, error rate) and respond by shedding
    load (skip optional stages), not by silently degrading quality or
    security checks.
  - GRACEFUL DEGRADATION AND DETERMINISTIC SAFE FALLBACK: when the
    Control Plane cannot complete its own processing, the safe fallback
    is deterministic and previously defined (Section 11's failure/
    fallback model, extended here to cover Control Plane self-failure, not
    only individual optimization-stage failure) — never an undefined or
    best-effort state.
  - The Control Plane must not consume more latency or cost than the
    optimization value it provides for the request class it is serving;
    this is the operational counterpart to NFR-009 and is stated formally
    as NFR-014 (Section 24).

OBJ-025 and NFR-014 are the anchors for this subsection.


52.4 VERIFIED NET OPTIMIZATION ECONOMICS (H04)
--------------------------------------------------
Token reduction alone has never been sufficient success criteria in this
document (see Section 1, Section 9, OI-002, Section 18). This subsection
makes the full accounting explicit and mandatory for every optimization
that is enabled by default or reported as a saving.

Net Optimization Value must account for:
  - Tokens saved
  - Model/inference cost saved
  - Optimization compute overhead (Section 52.3)
  - Retrieval cost
  - Routing cost
  - Cache overhead (write, storage, invalidation — see CE-001)
  - Additional latency introduced by the optimization itself
  - Retries caused by the optimization (e.g., escalation after a failed
    cascade, re-prompt after schema failure)
  - Quality degradation, weighted by the applicable quality gate
  - Task failure or regression attributable to the optimization
  - Downstream/tool cost where the optimization changes tool usage

A technique is counted as a saving only when this full accounting is net
positive and quality gates (Section 9) pass. Where any term cannot be
measured, the result is marked `unverified` per Section 8/AC-002 and
excluded from reported savings — it is never assumed favorable.

This is stated as a conceptual/heuristic decision framework (see the
clarification appended to Section 44): it governs what must be measured
and how a technique is judged, not a literal per-request constraint-solver
computation. Individual net-value estimates may be produced synchronously,
asynchronously, or via precomputed heuristics per Section 52.1.

OBJ-026 is the objective anchor for this subsection.


52.5 ENTERPRISE SPEND GOVERNANCE (H05)
-------------------------------------------
The framework shall support configurable spend controls at each of the
following scopes, independently: tenant, organization, user, and
application.

REQUIREMENTS
  - Each scope may define a spend limit (absolute and/or rate-based).
  - Runaway-cost protection: the framework must detect abnormal cost
    acceleration (e.g., an agent loop or fan-out of sub-agents driving
    spend far above historical baseline) and act before the configured
    limit is exhausted, not only after.
  - Circuit breakers: when a scope's spend limit is reached or a runaway
    pattern is detected, the framework must be able to halt or throttle
    further spend for that scope while leaving unrelated scopes
    unaffected (tenant isolation, Section 13.2 of `conventions.md`,
    applies here).
  - Budget-aware routing/execution: model routing (T0.1), reasoning
    budget (T0.3), and agent continuation (T3.1) decisions may consider
    remaining budget as an input signal.
  - SAFE BEHAVIOR ON EXHAUSTION: when a budget is exhausted mid-execution,
    the system follows the BUDGET EXHAUSTION handling already defined in
    Section 51.5 (return PARTIAL, remaining-budget = 0, never silently
    overspend, per-section breakdown of consumption).
  - Per SEC-011, budget controls are evaluated independently of, and
    never as a substitute for, security, authorization, and policy
    enforcement. A request that is within budget but fails authorization
    is still rejected; a request that is authorized but over budget is
    still halted.

OBJ-027 and SEC-011 are the anchors for this subsection.


52.6 VERIFIER CONFIDENCE AND CALIBRATION (H06)
----------------------------------------------------
Verification (AR-004 Verifier-Guided Escalation, QO-002 Quality-Aware
Fallback, the Quality Gates of Section 9) is a first-class concern in its
own right, not an implementation detail of the techniques that consume it.

REQUIREMENTS
  - Every verifier (unit tests, schema validation, type checking, static
    analysis, business rules, citation checks, format validation,
    semantic-equivalence checks, task-success checks, LLM-based judges)
    must expose a confidence signal, not only a binary pass/fail, wherever
    the verifier type supports one.
  - A verifier's output is not automatically ground truth merely because
    a verifier exists. Deterministic verifiers (unit tests, schema/type
    checks) are treated as higher-confidence than probabilistic verifiers
    (LLM-judge semantic-equivalence checks), and the acceptance threshold
    must reflect that difference.
  - Calibration: where a probabilistic verifier is used to gate an
    optimization (e.g., accepting a compressed context as
    semantically-equivalent, or accepting a cascade's low-cost-model
    output), its confidence score must be calibrated against ground-truth
    outcomes on a benchmark set before it is trusted in production
    (Section 45's maturity model applies to verifiers themselves).
  - Regression detection: a verifier's acceptance behavior must be
    monitored over time; a verifier that starts accepting results it
    previously rejected (or vice versa) without a corresponding change in
    the underlying technique is itself a signal requiring investigation
    (extends EL-005 to cover verifier drift, not only technique drift).
  - Acceptance thresholds are configurable per task/intent/tenant and
    subject to the same fallback discipline as any other quality gate
    (Section 9, QO-002): below threshold, restore the previous
    representation or escalate — never silently accept.

OBJ-028 is the objective anchor for this subsection.


52.7 DATA GOVERNANCE (H07)
--------------------------------
REQUIREMENTS
  - CLASSIFICATION: content admitted to any optimization stage must be
    classifiable as sensitive (which may include PII/PHI/PCI/secrets
    where applicable to the deployment) versus non-sensitive, and
    classification must be available before caching, compression, or
    retrieval decisions are made. Sensitivity classification is a Tier 0
    (SEC-protected) concern under Section 51.4 and is never pruned,
    compressed away, or deduplicated out on the basis of relevance score
    or budget pressure alone.
  - ENCRYPTION: sensitive data held by the Control Plane (in caches,
    memory, ledgers, logs, or traces) must be encrypted at rest and in
    transit according to the organization's configured policy.
  - RETENTION: every cache, memory layer (Section 34, CL-006), ledger, and
    log/trace must have a configurable retention period; the default is
    the organization's policy, never an unbounded retention assumption.
  - DELETION / ERASURE PROPAGATION: per SEC-013, a deletion or erasure
    request must propagate to every surface listed there. The framework
    must be able to report which surfaces still hold data derived from a
    given source after a deletion request, so propagation can be
    verified, not merely asserted.
  - DATA RESIDENCY: where a provider/model optimization profile
    (Section 41) declares a compliance/data-residency constraint, routing
    and caching decisions must honor it; the framework does not assume
    any specific residency requirement applies unless the deployment's
    own configuration establishes it.
  - TENANT ISOLATION: unconditional, per the existing Section 13.2 rule in
    `conventions.md` and SEC-003/SEC-010 above — restated here as a data-
    governance requirement, not only a caching requirement.
  - SUBPROCESSORS / EXTERNAL SYSTEMS: where an external system (a
    provider, a tool, an MCP server) processes data on the Control
    Plane's behalf, the same classification, retention, and deletion-
    propagation obligations apply to what the Control Plane sends it,
    to the extent the Control Plane controls that data's lifecycle.
  - No specific regulation (e.g., GDPR, HIPAA, PCI-DSS) is asserted to
    apply by this document. Applicability is established by the
    deployment's own scope and jurisdiction, not assumed here.

OBJ-029, SEC-012, and SEC-013 are the anchors for this subsection.


52.8 CODING-AGENT INTEGRATION FEASIBILITY TIERS (H08)
-----------------------------------------------------------
Complete interception of a coding-agent's requests cannot be assumed for
every target platform. The framework recognizes the following feasibility
tiers, from most to least capable:

  TIER 1 — DEEP / NATIVE INTEGRATION
    The Control Plane is embedded in or tightly coupled to the agent
    runtime and can observe and transform the full model-bound context
    before every inference call.

  TIER 2 — GATEWAY / INTERCEPTION INTEGRATION
    The Control Plane sits as an API/LLM gateway proxy (Section 4,
    Integration Mode 1) between the agent and the model provider and can
    observe/transform the request and response at that boundary.

  TIER 3 — PLUGIN / EXTENSION INTEGRATION
    The Control Plane runs as a plugin or extension inside the agent
    platform's own extensibility surface, with whatever context access
    that surface grants — typically less than Tier 1 or 2.

  TIER 4 — PROTOCOL / TOOL-LEVEL INTEGRATION
    The Control Plane participates as an MCP server or tool the agent
    calls; it can optimize what passes through that specific protocol
    surface but has no visibility into the rest of the agent's context.

  TIER 5 — ADVISORY / OBSERVABILITY-ONLY INTEGRATION
    The Control Plane can only observe telemetry the platform chooses to
    expose (e.g., logs, usage metrics) and can advise but cannot
    transform or block anything.

REQUIREMENTS
  - Every coding-agent integration (Cursor, Claude Code, GitHub Copilot,
    Antigravity, Codex, and comparable platforms) must declare which tier
    applies, and the declared tier bounds which of the DA-001 through
    DA-025 developer-agent optimization modules can actually be applied
    for that platform.
  - The exact mechanism used to achieve a given tier for a given platform
    is an architecture decision (`architecture.md`), not specified here.
  - The framework must degrade its claims accordingly: it must not report
    or imply full-pipeline optimization coverage for a platform where only
    Tier 3-5 access exists.

OBJ-030 is the objective anchor for this subsection.


52.9 MEMORY AUTHORITY (H09)
---------------------------------
An agent may own and manage its own working memory (short-term task
state, scratch reasoning, locally cached facts). This is expected and is
not restricted by this document.

That working memory is never authoritative over:
  - Control Plane execution state (Section 51.2, Domain 1)
  - Authorization state
  - Policy state (the pinned policy version of Section 51.8)
  - Authoritative external state (the actual current content of a file,
    ticket, or API resource)
  - Current context/workflow versions (Section 51.2, Domains 2 and 3)

CONFLICT RESOLUTION
  When agent-owned memory disagrees with Control-Plane-owned execution
  truth (for example: the agent's memory says a step is complete, but the
  execution's completed_actions set says it is not; or the agent's memory
  holds a permission grant that the current authorization state has since
  revoked), the Control-Plane-owned state is authoritative and the
  disagreement must be surfaced, not silently resolved in the agent's
  favor. The resolution path follows the same reconciliation model as a
  resume operation (Section 51.6): re-validate against current
  authorization, policy, model availability, and completed-actions state
  before trusting agent-reported memory.

This subsection is a direct restatement, for agent memory specifically,
of the general principle already established in Section 51 that the
system must never make an optimization decision using a stale snapshot of
context, policy, permissions, or resource state.

OBJ-031 is the objective anchor for this subsection.


52.10 REFLECTION AND LOOP AWARENESS (H10)
-------------------------------------------
See the direct amendment to AL-002 (Section 37) for the normative
requirement: repeated agent iteration may represent productive progress,
reflection/self-correction, a justified retry, redundant work, oscillation,
or a failure loop, and the Loop Waste Detector must classify against
expected task value and evidence of progress rather than against iteration
count alone. AL-001 (Agent Loop Progress Meter) supplies the underlying
per-iteration signals (state change, objective progress, errors
introduced/resolved) this classification depends on.

The Agent Stop Controller (T3.1, Section 6.20) and Agent Task Value/Early
Exit (AL-006) already stop workflows on insufficient expected value; this
subsection clarifies that the same expected-value lens applies to the
decision to CONTINUE a loop, not only the decision to stop one.


52.11 TOOL / MCP TRUST BOUNDARY (H11)
-----------------------------------------
Per SEC-014, tools and MCP metadata are part of the security/control
boundary, not merely a functional integration surface.

REQUIREMENTS
  - IDENTITY: a tool/MCP server's identity must be established
    (authenticated) before its capability metadata is trusted.
  - CAPABILITY METADATA AND SCHEMA INTEGRITY: tool/function schemas
    (consumed by DA-008 Tool Schema Optimizer and TE-002 Tool Argument
    Optimizer) must be validated for integrity; a schema that changes
    unexpectedly between calls is treated as a staleness/trust event, not
    silently accepted.
  - AUTHORIZATION: a tool call is authorized independently of whether it
    is cost/token-efficient; TE-001's ROI predictor never substitutes for
    an authorization check.
  - VERSIONING: tool/MCP versions are tracked so that a cached tool
    result (T3.3, Section 6.22) or a cached tool schema can be invalidated
    when the underlying version changes (extends CL-003 Dependency-Aware
    Cache Invalidation to tool/MCP version changes specifically).
  - AVAILABILITY AND STALE METADATA: a tool index used for dynamic
    tool/MCP selection (DA-007, TE-003) must be revalidated on a policy-
    defined interval; a tool discovered as available must not be assumed
    to remain available or unchanged indefinitely.
  - MALICIOUS OR MUTATED TOOL RESULTS: a tool result is untrusted content
    by default and is subject to the prompt-injection/content-integrity
    screening of Section 52.14 (SEC-016) before it is admitted to context,
    in addition to the existing Tool Output Filter (T3.2) and Tool Result
    Value Filter (TE-006) requirements.

OBJ-032's cross-execution concurrency framing and SEC-014 both anchor
parts of this subsection; the primary anchor is SEC-014.


52.12 SHARED STATE AND CONCURRENCY ACROSS EXECUTIONS (H12)
-------------------------------------------------------------
Section 51 defines execution truth for a single execution. This
subsection extends the same discipline to multiple agents, sub-agents, or
workflow executions that read or mutate shared resources concurrently
(shared files, tickets, shared memory layers per CL-006, or external
systems).

REQUIREMENTS
  - CONCURRENT MUTATIONS: when two executions mutate the same underlying
    resource, the framework must detect the conflict rather than let the
    second write silently overwrite context the first write depended on.
  - STALE DECISIONS: a decision made using a snapshot of shared state that
    has since changed is treated as a stale-result case under Section
    51.9 and must be re-validated before being relied upon by another
    execution.
  - RACE CONDITIONS AND VERSION CONFLICTS: shared resources that
    participate in cross-execution coordination carry a version (or
    equivalent conflict-detection token); an execution that acts on a
    version older than the current one must reconcile before proceeding,
    using the same reconcile-not-replay discipline as Section 51.6.
  - RECONCILIATION: where two executions' completed actions overlap
    (e.g., two sub-agents both attempted the same fix), the framework
    must reconcile to a single consistent outcome rather than applying
    both.
  - LOCKING / COORDINATION: where the shared resource or action is
    non-idempotent and concurrent access is possible, the framework must
    support locking or equivalent coordination sufficient to prevent
    conflicting concurrent side effects; this is required only where
    non-idempotent, concurrently-reachable side effects are possible, not
    universally.
  - IDEMPOTENCY: non-idempotent operations (Section 51's existing
    principle) must not be blindly replayed across executions any more
    than within a single execution's resume path.

OBJ-032 is the objective anchor for this subsection.


52.13 HUMAN APPROVAL FOR CONSEQUENTIAL ACTIONS (H13)
--------------------------------------------------------
Per SEC-015, a designated subset of actions — selected by policy or risk
classification (e.g., irreversible external side effects, high-cost
commitments, actions affecting production systems or other users) —
requires explicit human approval before execution.

REQUIREMENTS
  - The designation of which actions require approval is a policy
    decision, configurable per tenant/workflow, not a fixed universal
    list in this document.
  - Not every action is human-approved: routine, reversible, low-risk
    actions proceed under the advisory/enforcement/execution-ownership
    model of Section 52.2 without a human-approval gate, or the
    Control Plane's own value proposition (reducing unnecessary
    interaction) is defeated.
  - An action pending approval follows the same interruption/partial-
    execution handling as any other suspension cause (Section 51.5):
    checkpoint, return PARTIAL or a explicit AWAITING_APPROVAL status, and
    resume per Section 51.6 once approval is granted or denied.
  - Approval (or denial) is recorded in the audit record alongside the
    decision it gates, per Section 52.15.

SEC-015 and OBJ-033 are the anchors for this subsection.


52.14 PROMPT INJECTION AND MALICIOUS CONTENT (H14)
--------------------------------------------------------
Per SEC-016, retrieved content, tool output, sub-agent results, and any
other externally-sourced context are untrusted by default.

REQUIREMENTS
  - ORDERING: content-integrity/prompt-injection screening runs before
    any optimization stage is permitted to admit, rank, compress, cache,
    or otherwise act on that content, and before it can be used to
    authorize a tool call or other action. Optimization decisions
    (Section 52.1's Optimization Decision Engine, OI-001) must not admit
    content ahead of this screening in the interest of latency.
  - This ordering resolves any apparent tension with Section 52.1's
    preference for hybrid/precomputed evaluation: precomputation may
    speed up the screening itself (e.g., a precomputed classifier), but
    it may not be skipped or deferred until after admission.
  - SCOPE: this applies uniformly to RAG chunks, search results, tool
    outputs, sub-agent handoffs (AL-005), and MCP tool results (Section
    52.11), not only to the end-user's direct input (which the existing
    T1.1 Sanitizer already addresses).
  - FAILURE MODE: a screening failure (inability to complete the check)
    is a security/integrity failure, not an optimization failure, and
    therefore fails closed per Section 51.10 and the non-negotiable
    fail-open/fail-closed distinction in `conventions.md` — it must
    reject or quarantine the content, never silently admit it because the
    check itself failed.

SEC-016 and OBJ-034 are the anchors for this subsection.


52.15 DECISION EXPLAINABILITY AND AUDIT (H15)
---------------------------------------------------
Per the strengthened NFR-010 (Section 24), the following decision
categories must produce a retrievable explanation, not merely a best-
effort one:

  - Why context was admitted or pruned (T1.9, T1.10, CL-004's provenance
    records supply the mechanism)
  - Why a model/provider was selected (T0.1, AR-001)
  - Why a cache entry was reused or rejected (T1.6, T1.7, Section 51.9
    stale-result rejection)
  - Why an optimization stage was skipped (OI-002's cost-of-optimization
    controller, OI-003's depth controller)
  - Why an execution was blocked, recovered, or superseded (Section
    51.5-51.9)
  - Why a fallback occurred (Section 11, Section 51.10)

REQUIREMENTS
  - Each of these decisions must be logged with enough structured detail
    (the inputs considered, the rule/model/threshold applied, the
    resulting action) to reconstruct the reasoning during audit or
    debugging, consistent with SEC-008 (all optimization transformations
    must be auditable).
  - This requirement is about retrievability of the explanation, not
    about surfacing it to the end user by default; presentation is an
    interface/architecture decision.

NFR-010 (as strengthened) is the anchor for this subsection.


52.16 EXECUTION STATE PORTABILITY (H16)
-------------------------------------------
The checkpoint content defined in Section 51.6 (execution_id,
execution_version, context_version, workflow_version, completed_actions,
unresolved_questions, token_ledger_snapshot, policy_version,
model_selected, reversibility_records) is specified in provider/session-
neutral terms: none of those fields is defined as, or requires, a
specific model provider's session object, conversation-thread ID, or
proprietary state format.

REQUIREMENTS
  - Resumable execution must not be inherently tied to one model,
    provider, or session implementation. A checkpoint produced under one
    model/provider selection must remain interpretable for reconciliation
    (Section 51.6, step-by-step) even if `model_selected` changes on
    resume (for example, due to a provider outage triggering failover
    per Section 51.5).
  - Where a provider or session mechanism exposes its own native
    resumability (e.g., a provider-side conversation/session ID), the
    Control Plane may use it as an optimization (avoiding re-transmission
    of cached context) but must not make correctness of resume/
    reconciliation depend on that provider-specific mechanism being
    present.
  - The exact serialization/storage format for checkpoint state is an
    architecture/interface decision and is not specified here.

This subsection extends the checkpointing/resumability requirement of
Section 51.6 with a portability constraint; no new objective ID is
introduced because it refines an existing requirement rather than adding
a new category of one.


52.17 LAYER 3 BOUNDARY: INTEGRATION, NOT IMPLEMENTATION (H17)
--------------------------------------------------------------------
See the direct amendment to Section 42 for the full normative requirement:
the Control Plane's role at the inference/serving layer is awareness,
integration, routing, policy, and capability negotiation with
infrastructure/providers. It does not implement KV-cache engines,
continuous batching, speculative decoding, quantization, or prefill/
decode disaggregation itself; those remain infrastructure/provider-owned
mechanisms the Control Plane integrates with. This resolves the ambiguity
in the original Section 42 wording ("the control plane may extend below
the API boundary") that could otherwise be read as a mandate to build
these mechanisms.


52.18 TOKEN, CONTEXT, CACHE, AND INFERENCE OPTIMIZATION: OWNERSHIP
        BOUNDARIES (H18)
------------------------------------------------------------------------
See the direct amendment to Section 1 for the summary statement. The full
distinction:

  - PROMPT / INPUT TOKEN OPTIMIZATION — sanitization (T1.1), query
    compression (T2.1), entity extraction (T1.3). Owned and implemented
    directly by the Control Plane.
  - OUTPUT / REASONING TOKEN OPTIMIZATION — reasoning budget control
    (T0.3), output length control (Section 6.19), output schema
    selection (Section 6.18). Owned and implemented directly.
  - CONTEXT OPTIMIZATION — retrieval, ranking, pruning, dedup,
    compression, reordering, budgeting (Layer 2, Section 43). Owned and
    implemented directly.
  - CACHE OPTIMIZATION — prompt cache, semantic cache, tool-result cache,
    cache economics (Section 35). Owned and implemented directly, but
    built on provider-exposed cache primitives where the provider
    supplies them (Section 6.7's provider-neutral abstraction
    requirement).
  - MODEL / PROVIDER ROUTING — Owned and implemented directly (T0.1,
    Section 6.23, AR-001); the decision is the Control Plane's, even
    though execution happens on the provider's infrastructure.
  - INFERENCE-RUNTIME OPTIMIZATION — Layer 3 (Section 42, Section 52.17).
    Awareness, integration, routing, and policy only; implementation is
    infrastructure/provider-owned.

This taxonomy is the basis for the "must stay measurement-separate"
requirement already stated for Layer 3 in Sections 42 and 43: measuring
these six categories together would make it impossible to attribute a
saving or a regression to its actual cause.


52.19 RESEARCH CLAIMS AS EVIDENCE, NOT GUARANTEES (H19)
-------------------------------------------------------------
This principle is already extensively established in this document
(Section 1's "No optimization shall be considered successful solely
because it reduces token count", Section 12/13/14's benchmarking
requirements, Section 16's treatment of source whitepaper benchmarks,
Section 17's research-supported techniques, Section 28's reference
validation and correction of a misattributed arXiv ID, AC-018, and
Section 49's outside-world validation notes distinguishing research
evidence, provider capability, local benchmark result, production policy,
and production guarantee).

The Architecture Hardening Pass reaffirms this principle without
weakening or restating it as a new obligation: no benchmark percentage
from LLMLingua, LongLLMLingua, LLMLingua-2, RouteLLM, FrugalGPT, or any
other cited source, and no future research citation added to this or
derived documents, may be hard-coded as an expected production result.
Section 45's maturity model (LEVEL 0 RESEARCH through LEVEL 5 AUTO-TUNED)
remains the required path from citation to production claim.


52.20 ANTI-SCOPE: WHAT THE CONTROL PLANE IS NOT (H20)
-------------------------------------------------------------
See the direct amendments to Sections 1, 25, and 48 for the anti-pattern
statements. Restated here as an explicit boundary:

The Control Plane shall NOT become:
  - A replacement agent orchestrator. It optimizes what an orchestrator
    sends to and receives from models/tools; it does not replace the
    orchestrator's planning/control logic (see Section 52.2's advisor/
    enforcer boundary).
  - A model-training system. It may inform which model is selected
    (routing, cascade) but does not train, fine-tune, or own model
    weights.
  - A model-runtime infrastructure platform. Per Section 52.17, it
    integrates with KV-cache/batching/serving infrastructure; it does not
    become that infrastructure.
  - Provider infrastructure. It sits between applications/agents and
    providers via adapters (Section 4); it is not itself a model
    provider.
  - A general-purpose developer IDE. It optimizes the context and calls a
    coding agent makes; it does not provide the editing/IDE experience
    itself.
  - A UX replacement for coding agents. Per Section 52.8, its integration
    depth into a given coding-agent platform is bounded by that
    platform's actual feasibility tier; it does not present itself as an
    alternative front end to the coding agent.

Where any of these adjacent systems is needed, the Control Plane
integrates with it through the adapter/integration-mode layer (Section 4)
rather than reimplementing it.

OBJ-035 is the objective anchor for this subsection.


52.21 ADDITIONAL ACCEPTANCE CRITERIA (HARDENING PASS, 2026-09-15)
---------------------------------------------------------------------
AC-039:
The framework must declare, per decision type, which operating mode
(synchronous, asynchronous/precomputed, or hybrid) it uses, and must
account for its own decision latency/overhead as part of net-value
accounting.

AC-040:
The framework must record, for every advisory, enforcement, or execution-
ownership decision, which of the three categories applied.

AC-041:
The framework must enforce its own latency and cost budgets and degrade to
a deterministic safe fallback under overload rather than degrading
application correctness or security.

AC-042:
The framework's net-optimization-value accounting must include
optimization overhead, retrieval/routing/cache overhead, added latency,
retries, quality degradation, and task failure/regression, not tokens
alone.

AC-043:
The framework must support spend limits and circuit breakers at tenant,
organization, user, and application scope, and must never allow a budget
decision to substitute for a security/authorization/policy decision.

AC-044:
The framework must expose a calibrated confidence score for probabilistic
verifiers and a configurable acceptance threshold before that verifier's
output gates an optimization decision.

AC-045:
The framework must support sensitivity classification prior to
optimization admission and must be able to report which surfaces (cache,
memory, ledger, log/trace) still hold data derived from a given source
after a deletion request.

AC-046:
Every coding-agent integration must declare its integration feasibility
tier (deep/native, gateway/interception, plugin/extension, protocol/tool-
level, or advisory/observability-only).

AC-047:
The framework must detect and surface, not silently resolve, a conflict
between agent-owned working memory and Control-Plane-owned execution/
authorization/policy state.

AC-048:
The framework must authenticate tool/MCP identity and validate schema/
capability metadata integrity and staleness before trusting a tool result.

AC-049:
The framework must detect concurrent mutation, stale decisions, and
version conflicts across multiple agents/sub-agents/executions sharing a
resource, and must not blindly replay non-idempotent operations across
executions.

AC-050:
The framework must support a policy-configurable human-approval gate for
designated consequential/irreversible actions, without requiring approval
for every action.

AC-051:
The framework must run prompt-injection/content-integrity screening on
externally-sourced content before any optimization stage admits, ranks,
compresses, caches, or acts on that content, and must fail closed if the
screening itself cannot complete.

AC-052:
The framework must retain a retrievable explanation for context admission/
pruning, model/provider selection, cache reuse/rejection, optimization
skip, execution block/recovery/supersession, and fallback decisions.

AC-053:
Checkpoint/resume state must remain interpretable for reconciliation
across a change in selected model/provider and must not require a
specific provider's native session mechanism to be correct.
